3三条铁证：RAG 真的在干活

✓重排阶段真实执行

trace 里出现 pipeline.chunk_rerank → rerank [GENERATION] model=llm-rerank，耗时 1284ms、消耗 2193 tokens。 这是旧版从没有过的——旧版本 chat 路径每次都跳过重排。等于说：检索出的候选块，被逐个重新打过分。

↻查询被改写后才去检索

pipeline.query_understand 下挂了 2 次 chat.completion（deepseek-chat，2338+239 tokens）。 说明系统先把口语问题改写成检索友好的查询，才交给检索引擎——这是纯 LLM 直答不会做的事。

◎答案逐块可溯源

回答里嵌入 <kb doc="…" chunk_id="…">。本次命中 5 个块，覆盖 2 篇文档、 4 种块类型（text / summary / table_column / table_summary）， score 均为 1。数字（3860 万 / 12 个月 / 238,000 元）与原文逐字一致。

4怎么自己看到（三种方式）

按"想看到什么"选。做演示推荐 A，做排查推荐 B。

A. 界面时间线 —— 演示时最有说服力

  1. 打开 WeKnora 网页

    登录后进入任一知识库的聊天。

  2. 先确认当前是 RAG 模式

    RAG / 快速问答模式下才会出现检索步骤；Agent 模式走的是另一套（工具调用）展示。

  3. 随便问一个只有文档里才有的问题

    例如"星海园区的总预算是多少"。回答上方的步骤树会边生成边长。

  4. 点"知识检索"那一步

    右侧滑出引用抽屉，能看到命中的原文块与来源文档——这就是"答案从哪来"。

B. Langfuse —— 排查与量化

  1. 浏览器打开 http://localhost:3000

    自建实例，账号在 .env 里（LANGFUSE_INIT_USER_EMAIL）。

  2. 进 Traces，按 sessionId 过滤

    每条 POST /api/v1/knowledge-chat/:session_id 就是一次问答。

  3. 展开树，看每个 span

    耗时、token、模型一目了然；点 rerank 能看它给每个候选块打的分。

# 不想开浏览器？命令行直接拉 trace（已验证可用）
export PK=pk-lf-...  SK=sk-lf-...
curl -s -u "$PK:$SK" "http://localhost:3000/api/public/traces?limit=5"
# 或只取某次问答的完整树
curl -s -u "$PK:$SK" "http://localhost:3000/api/public/traces/<trace_id>"

5"证明 RAG 有用"该拿什么比

光看链路跑通还不够。要让"有用"成立，得拿出对照。三个最省力的实验：

1问文档外的知识

问一个库里根本不存在的实体（如"AI 训练芯片"），RAG 会明确答"未找到"并给出相邻信息，而不是编。这是防幻觉的直接证据。

2问内部专有数字

问"总预算""设备单价"这类 LLM 无从得知的值，RAG 能给出带 chunk_id 溯源的精确答案。纯 LLM 只能瞎猜。

3看引用得分与重排

在 Langfuse 里对比 retrieve 的候选集与 rerank 之后的排序——重排把相关的顶上来，顺序变了，这就是重排的价值。

结论

不用改任何工具。 你要的"看见 RAG 过程"，WeKnora 已经内置：日常演示用界面时间线，量化排查用 Langfuse， 写脚本用 SSE / _debug_events。Langfuse 不是可有可无的装饰——它是唯一能把"检索了几路、重排花了多久、 每步烧了多少 token、跨进程的入库任务挂在哪"一次性摊开的地方。

⚠️ 顺带发现一个必须知道的状态变更

运行中的 app 已经不是官方 v0.8.0 镜像了。现在 /system/info 返回：

  • version = v0.7.1，而 commit_id / build_time / go_version 全是 unknown
  • 启动时间 2026-09-10T10:26:07Z（北京时间 18:26）

这是用本地源码编译出的二进制被部署上去了的特征（无 ldflags 注入 → 版本信息落空）。 好消息：之前一直"未生效"的 rerank 兜底补丁已经真的在跑了（Langfuse 为证）。 代价：app 基线从 v0.8.0 降级到了 v0.7.1，而数据库已被 v0.8.0 迁移过（db_version 90）。 建议核实这次降级是否有意为之，并确认三处 Go 补丁的目标基线。
