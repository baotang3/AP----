WeKnora：把「文档」变成可被 Agent 调用的知识底座

WeKnora 是腾讯开源的企业级 RAG 知识框架。它做的事情可以一句话概括： 把散落的原始文档，加工成机器可检索、可推理、可追溯的知识资产，再通过 MCP 把这套能力交给任意 Agent 使用。 本页聚焦三件事——它到底解决什么问题、接上 MCP 之后 Agent 能做什么、 以及最核心的「知识入库」与「知识检索」两条链路各自怎么实现、用了什么技术、彼此是什么关系。

01

项目作用：它到底解决什么问题

大模型本身不知道你公司的文档。把文档直接塞进上下文有三个硬伤：太长塞不下、太贵、找不到关键段落。 WeKnora 的价值就是在「原始文档」和「大模型」之间建一层工程化的中间层。

① 解决「塞不下」

把长文档切成分块（chunk）并预先算好向量与关键词索引。 提问时只取最相关的几块，而不是把整本书送给模型。

② 解决「找不到」

单靠向量相似度会漏掉专有名词和精确匹配。WeKnora 用 向量 + 关键词双路召回，再用 RRF 融合，最后重排精挑出真正有用的段落。

③ 解决「不可信」

每个回答都带来源引用，能回溯到具体文档与分块。 这是它区别于「聊天玩具」、能进企业场景的关键。

三大能力形态

同一套知识底座，对外暴露三种使用方式，复杂度递增：

RAG 问答确定性

固定流水线：检索 → 融合 → 重排 → 生成。 一次检索，一次回答，路径可预测、延迟低。

ReAct Agent自主

模型自主决定调哪个工具、调几次：可以先查知识库、再查图谱、 不够就联网搜索，多轮迭代后才回答。

Wiki 模式结构化

入库时就把文档重写成互相链接的百科页面， 检索时可以沿着链接扩散，适合方法论、制度这类成体系的资料。

02

通过 MCP 接入 Agent 之后，能实现哪些功能

这里有个容易混淆的点：WeKnora 同时扮演 MCP 的两个角色。 搞清方向，才知道「接入」究竟接的是什么。

A · 服务端

WeKnora 提供工具，外部 Agent 来调用

它把知识库能力包装成一个 MCP Server（Python 实现，共 28 个工具）。 任何支持 MCP 的客户端（Claude Desktop、Cursor、DSH 等）挂上它之后， 模型就「长出了」读写知识库的手脚。

外部 Agent ──MCP 协议──▶ WeKnora MCP Server ──▶ 知识库 / 图谱 / Wiki

本机就是这样接的：DSH 把仓库里的 mcp-server/run_server.py 注册成 mcp__weknora__* 系列工具，共 28 个。

B · 客户端

WeKnora 作为调用方，去用别人的工具

它的内置 Agent 也可以挂载外部 MCP 服务， 把企业已有的系统（工单、ERP、内部 API）变成 Agent 可调用的工具。

内置 Agent ──MCP 协议──▶ 外部 MCP Server（工单 / ERP / …）

两个方向互不冲突，可以同时开启：它既是知识库的提供方，也是其他系统的消费方。

接上之后，Agent 具体多出哪些能力

按「能做什么事」归类，而不是按工具名罗列：

另外还有一层：内置 Agent 的工具

上面的 28 个是对外暴露的 MCP 工具；WeKnora 自己的 ReAct Agent 还内置了一套工具， 两者是不同层面。检索相关的内置工具里最关键的是 knowledge_search：

坑一（配置硬约束）：内置 Agent 只要启用了 knowledge_search， 就必须为这个 Agent 单独绑定重排模型（rerank_model_id）， 否则会直接报错 rerank model is not configured。 这是它和普通 RAG 问答的一个硬性差异——普通问答走全局重排配置，Agent 走自己的。
坑二（命名陷阱，我实地验证过）：Agent 内置工具里有一个叫 query_knowledge_graph 的工具，名字看着就是「查图谱」。 但读源码会发现，它在 internal/agent/tools/query_knowledge_graph.go 里 调用的其实是 HybridSearch，根本不会碰到图数据库； 该文件里甚至明确写着一行 Full graph query language (Cypher) support is under development。 所以它实际上是「混合检索 + 把你的图谱抽取配置读出来展示给你看」，而不是真正的图查询。 真正会走图谱的是对话检索链路内部的实体检索（见下一节），不是这个工具。
03

知识入库：把文档变成索引（写链路）

入库的目标不是「存起来」，而是预先把所有未来检索需要的东西都算好。 这是一条重成本、可异步、可失败重试的链路。

同步段（阻塞上传请求）

校验 → 落盘原始文件 → 建知识条目 → 投递任务。 很快，用户几乎立刻拿到返回。

异步段（asynq 队列）

解析 → 分块 → 嵌入 → 摘要 → 图谱 → 问题 → 图片理解 → Wiki。 慢，可能几分钟，失败可重试。

1
上传与校验Go · handler

接收文件，解析出「本次生效的处理配置」= 知识库默认值 + 本次上传覆盖项。 此处会做前置拦截：上传图片文件但没配视觉模型，直接拒绝，不会等到异步阶段才失败。

HTTP 上传配置合并与校验
2
原始文件落盘存储后端

按 租户/知识ID/时间戳.后缀 存原始文件。本机用本地存储 （/data/files/…），也支持 MinIO / COS 等对象存储。

local / MinIO / COS
3
文档解析Python docreader · gRPC

Go 通过 gRPC 把文件字节交给独立的 Python 解析服务，拿回 Markdown 正文 + 内嵌图片引用。解析引擎按文件类型路由—— PPTX / PDF / DOCX 走 anydoc，Markdown / HTML 走 builtin， CSV / TXT 走 simple。

关键设计：docreader 刻意保持轻量——它自己的文档字符串写着 「No chunking, no storage, no OCR, no VLM」。分块、存储、光学识别、视觉理解 全在 Go 侧做。这样解析服务可以独立扩缩容，也不会把模型依赖塞进解析进程。

gRPCanydocbuiltinsimplemarkitdown
4
图片资源落库与改写Go · image resolver

解析结果里的图片会被单独存为资源，Markdown 里的图片地址被改写成内部 resource URL。 同时有一道图标过滤：太小（任一边 < 64px）或太小（< 512 字节）的图直接丢弃， 避免把一堆装饰性小图送去理解。

资源服务图标过滤
5
分块 ChunkingGo · 纯代码，不调模型

把长文切成检索的基本单元。默认 512 字符 / 重叠 80， 分隔符优先级是「段落 → 换行 → 句号/问号等」。 strategy=auto 时先做一次结构画像，再决定用 标题感知 / 启发式 / 递归中的哪一档切法。

可选父子分块：小的子块用于向量匹配（命中更准），命中后返回大的父块给模型（上下文更全）。 这是「检索精度」和「上下文完整度」之间一个很实用的折中。

512 / 80strategy=auto父子分块 4096/384
6
向量化嵌入模型

每个分块送嵌入模型算出向量，写入向量索引。本机用本地 Ollama 上的 bge-m3，1024 维——维度必须和库里的索引列完全一致。

bge-m3 · 1024 维Ollama
7
文档摘要调 LLM

整篇文档交给大模型生成摘要，作为文档级的一等分块。作用是让「这篇讲什么」这类 宏观问题不必靠拼凑片段来回答。

LLMsummary 分块
8
后处理扇出（四路并发）调 LLM / VLM

这是入库最重、也最能体现设计意图的一步。四类任务各自独立投递到队列、并发执行， 互不阻塞——某一路失败不会拖垮整篇文档：

实体关系抽取

逐分块让 LLM 抽实体与关系，写进图数据库。 抽取规则（示例文本 / 关系类型 / 附加要求）由知识库配置决定。

问题生成（Doc2Query）

为每个分块生成若干「用户可能会问的问题」， 每个问题单独作为一条检索入口指向原分块。

图片多模态理解

每张图调两次视觉模型：一次光学识别（取图中文字）， 一次生成描述。产出两种子分块。

Wiki 页面生成

把文档重写成互相链接的百科页，含实体页、概念页、摘要页与目录。

9
写入索引检索存储

所有产出的分块（正文 / 摘要 / 图片识别 / 图片描述 / 生成的问题） 统一写入向量索引与关键词索引，成为可被检索的对象。

向量索引关键词索引
10
收尾与可观测编排层

等待所有子任务收敛，更新文档状态为「已完成」并重新启用检索。 每个阶段都会记录处理时间线，每次模型调用都上报到 Langfuse—— 出问题时能回答「是解析错了、还是分块错了、还是模型读错了」。

处理时间线Langfuse trace

为什么用「队列扇出」而不是一条直线走完

  • 成本与延迟不对称：分块不花钱也不慢，但图谱、问题、图片理解要调成百上千次模型。 混在一条流水线里，任何一步慢都会把整篇卡住。
  • 失败粒度不同：图谱失败不应该导致正文搜不到。拆成独立任务后，可以只重试失败的那一路。
  • 可开关：知识库上的四个开关（向量 / 关键词 / 图谱 / Wiki）决定扇出哪几路。 关掉图谱就完全不会有图数据库调用。
  • 可并发：按分块批量投递（问题生成每 20 个分块一批），多 worker 并行消费。

04

知识检索：把问题变成答案（读链路）

检索是一条同步、低延迟的链路。它不生成新知识，只负责 「在入库期已经算好的索引里，快速挑出最该给模型看的几块，并组织成上下文」。

它不是一段代码，而是一条插件链

实现上，检索被拆成一组「事件」，每个插件声明自己关心哪些事件， 运行时按注册顺序串成责任链。好处是：想加一路召回（比如新增 Wiki 加权、实体检索）， 只要插一个插件，不用改动主流程。

外部工具（如 DSH） │ └─▶ WeKnora MCP Server ──▶ REST API ──▶ 会话 ──▶ 检索插件链 ──▶ 答案 + 引用

本机实测：DSH 通过 MCP 调用 list_knowledge_bases / get_knowledge_base / list_knowledge / hybrid_search 等工具，全部正常返回。

1
加载会话历史event: load_history

取出多轮对话上下文。这是「它」「那个方案」这类指代能被理解的前提。

2
查询理解与改写event: query_understand调 LLM

这一步是检索质量的分水岭。用户的原始问句往往不适合直接拿去检索—— 指代不明、口语化、或需要拆成多个子问题。 这里会把问题改写成更适合检索的形式（查询扩展 / 多查询）， 有时也做结构化理解，把问题映射成「实体 + 意图」。

查询改写查询扩展查询理解
3
双路召回event: chunk_search / chunk_search_parallel

改写后的查询同时走两条路：

向量检索（语义）

把查询也嵌入成 1024 维向量，在库里按余弦距离找最近的分块。 强项是「意思相近但用词不同」。

关键词检索（字面）

BM25 全文匹配。强项是专有名词、编号、型号、缩写—— 这些恰恰是向量检索最容易漏掉的。

两路可以并行（多查询 / 多知识库时走 parallel 分支）。 这一步通常不做重排，只负责「尽量别漏」，所以召回数量放得比较宽。

4
RRF 融合服务层 · 纯算法

两路结果分数尺度不同（向量是余弦相似度，关键词是 BM25 分值，量纲完全不一样）， 不能简单相加。WeKnora 用的是基于排名的融合——只关心「排第几」，不关心「多少分」， 从而天然免疫尺度差异。

score = w_vector / (k + 向量排名) + w_keyword / (k + 关键词排名) 默认值： k = 60 w_vector = 0.7 w_keyword = 0.3

RRF 分数范围极小——按默认权重，两路都排第 1 时也只有 (0.7+0.3)/61 ≈ 0.016。正因如此，阈值过滤必须在融合之前完成： 融合后再拿 0.15 / 0.3 这种「相似度」量纲的阈值去筛，会把结果全部滤空。 这是实现上最容易搞错的地方。

5
实体 / 图谱检索event: entity_search · 由上一阶段的并行检索在内部调用可选

注意它不是一个与双路召回并列的顶层阶段。 并行检索阶段会在自己的流程里直接调用实体检索插件—— 从问题中识别出实体，拿实体去图数据库做节点检索，把命中的节点与关系收集起来。

这条路的价值在于：「A 和 B 之间是什么关系」这类问题，靠文本相似度几乎命中不了， 因为答案不在任何单个分块的文字里，而在关系结构里。 图谱结果会带上自己独立的匹配类型标记（区别于向量和关键词）， 并在合并前剔除已经在前两路出现过的分块，避免重复占用上下文预算。

图数据库节点检索独立的匹配类型结果去重
6
重排 Rerankevent: chunk_rerank效果提升最大的一步

召回阶段为了「不漏」会捞回几十条，其中必然混着大量弱相关结果。 重排用一个更贵但更准的模型对这几十条重新打分排序，再截取前若干条。

召回：广撒网（top 50） ──重排──▶ 精选（top 10）

WeKnora 的重排走统一的 HTTP 契约：向 {base_url}/rerank 发请求， 期望返回带 index 与 relevance_score 的结果数组。 所以任何满足这个契约的服务都能接——本机就是用一个 「用大模型打分」的适配服务顶上的。

RerankTopK = 10RerankThreshold = 0.2/{base_url}/rerank 统一契约
7
联网补充event: web_fetch可选

知识库里没有、或问题本身需要外部信息时，走联网搜索补充证据。 本机接的是自建 SearXNG。

8
上下文合并组装event: chunk_merge

把选中的分块拼成给模型的上下文。这一步不是简单拼接，而是包含几种「还原」：

  • 父块还原——命中子块时，改取它所属的父块，给模型更完整的上下文
  • 图片信息注入——把图片的光学识别文本与描述并入分块内容
  • 生成问题并入——入库期生成的问题也作为该分块的补充文本
  • 重叠去重——相邻分块有重叠区，合并时要去掉重复段落
  • 历史合并——把多轮对话的相关历史一并纳入

完整的 13 个事件阶段

上面 10 张卡片是按「一件事」合并后的讲法。代码里的原始阶段划分是 13 个事件—— 其中检索并行分支、数据分析、流式与非流式生成是独立事件，故数量更多：

load_history query_understand chunk_search chunk_search_parallel entity_search chunk_rerank web_fetch chunk_merge data_analysis into_chat_message chat_completion chat_completion_stream filter_top_k

紫色 = 需要调用大模型的阶段；绿色 = 检索链路本体；橙色 = 决定最终质量的重排； 灰色 = 可选或辅助能力。

两个容易看错的地方：①entity_search 虽然是一个独立事件， 但没有独立的顶层触发点，它是由 chunk_search_parallel 在内部调用的 ——所以它在地理上「嵌在」并行检索里面，而不是和双路召回平级。 ②chat_completion 与 chat_completion_stream 是同一个逻辑步骤的 非流式 / 流式两种实现，实际只会触发其中一个。

怎么理解这几个数

  • 50 → 10：召回要宽、精排要严。这是两阶段检索的经典比例。
  • k=60：k 越大，排名差异被抹得越平。语料大时通常调大，小时调小。
  • 0.7 / 0.3：向量为主、关键词为辅。中文资料里把关键词权重调高常常有效， 因为专有名词多。
  • 阈值在融合前：见上文，这是 RRF 的尺度决定的，不是随意选择。

这种「一套接口、多种后端」的设计，意味着换向量库不需要改业务代码，只换配置。 对本机来说，选 Postgres 的好处是向量、关键词、业务数据在同一个事务里， 不会出现「入库成功了但索引没建上」的不一致。

实际发出的向量检索 SQL（本机 Postgres 引擎）

SELECT … , embedding::halfvec(1024) <=> $1::halfvec(1024) AS distance FROM embeddings WHERE … ORDER BY embedding::halfvec(1024) <=> $1::halfvec(1024) LIMIT … -- 内层放大取数，保证 HNSW 的 ef_search 足够 … ORDER BY distance ASC LIMIT … -- 外层才是真正的 TopK
  • <=> 是 pgvector 的余弦距离算子，越小越相似。
  • 用 halfvec（半精度）而非全精度，索引体积减半、检索更快，精度损失对检索排序几乎无感。
  • 走的是 HNSW 近似最近邻索引，所以 ORDER BY 的表达式必须和索引表达式完全一致， 否则索引失效退化成全表扫描——这也是代码注释里特意强调的一点。
  • 「内层放大 LIMIT + 外层真 LIMIT」两层写法，是为了让 HNSW 有足够候选可挑。

入库与检索是什么关系

这是整套架构里最值得理解的一点。它们不是「两个功能」，而是同一条知识管线的 生产端与消费端——入库负责把所有昂贵的计算前置，检索负责在毫秒级把它取出来用。

一句话概括这层关系

入库是把「理解文档」的成本一次性付清，检索是低成本地反复消费这份理解。

如果没有入库阶段的预计算，每次提问都得现场读完所有文档——既慢又贵且必然塞不下。 这就是 RAG 相对于「把文档全塞进上下文」的根本优势所在。

入库：贵、慢、一次性 → 产出索引 检索：便宜、快、可重复 → 消费索引

配置如何耦合：入库少做一样，检索就少一路

知识库上有四个索引开关，它们直接决定入库会产出什么；而检索能用的召回路径， 严格受制于入库产出了什么。这是一条单行道：检索期无法凭空多出一路召回。

入库时的开关入库会产出检索时才能用上
vector_enabled 分块向量（1024 维） 向量语义召回——关掉就等于丧失了语义匹配能力
keyword_enabled BM25 全文索引 关键词字面召回——关掉则专有名词、编号容易漏
graph_enabled 实体与关系（Neo4j） 图谱召回 entity_search——关掉则「A 与 B 什么关系」类问题很难答
wiki_enabled 互相链接的百科页 Wiki 检索与链接扩散、wiki_boost 加权
问题生成配置 每个分块的若干「用户会问的问题」 多一路以「问法」为单位的召回入口，显著提升召回率
多模态开关 + 视觉模型 图片的图中文字与描述分块 图片内容可被检索到——否则 PPT 里的图表对系统完全不可见
最重要的一条实践结论：这些开关只影响解析时刻。 改完配置后，已经入库的文档不会自动重算—— 必须对文档做一次「重新解析」，新配置才会生效。这是使用中最常见的困惑来源。

本机实测：一条真实文档走完两条链路

以一个真实项目知识库为例（两篇咨询 PPT，共约 7 MB），四条索引管线全开，实测产出：

1701图谱关系数（1537 个实体节点）
314Wiki 页面（5541 条互链，孤儿页仅 5）
每块 3 个生成的问题作为额外检索入口
每图 2 次视觉模型调用（识别 + 描述）

入库侧观察到的

  • 图谱按配置的关系类型产出，前五类恰好是配置里指定的五种， 说明抽取规则被真正执行了
  • 作为「格式示例」用的无关领域文本没有污染图谱（泄漏节点数为 0）
  • 图片理解会把每张图拆成两个子分块：一个装图中文字，一个装描述
  • 装饰性小图会被过滤，纯色块返回空内容并被丢弃，不产生垃圾分块

检索侧观察到的

  • 向量、关键词双路召回后经 RRF 融合，再重排，最终取 top 10 进上下文
  • 每个回答都能回指到具体文档与分块
  • Agent 模式下可自主决定是否补充联网搜索，并把结果作为引用一并返回
  • 全链路在 Langfuse 上可见：每次模型调用的耗时与 token 用量都可追溯
