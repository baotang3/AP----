## 2.1　Agent 工作台后端

**一句话主轴**：把"一次可能跑几分钟的 Agent 任务"从 HTTP 连接里解耦出来。

**怎么讲：**

这块的技术栈是 FastAPI 加 Claude Agent SDK，数据库是 MySQL，用的 SQLAlchemy 2.x 异步 ORM。

我先讲最关键的一个设计决策：**Agent 的执行和 SSE 连接是解耦的。**

为什么？因为 Agent 跑一次任务，可能读文件、写文件、跑代码、来回好几轮，几分钟都正常。如果我把整个执行挂在 HTTP 连接上，用户一刷新页面、一断网，这次任务就白跑了，已经产出的东西也落不了库。

所以我的做法是：HTTP 请求进来之后，我起一个**独立的 producer 任务**去跑 Agent，这个任务**自己建一个数据库 session**——不能复用请求级的 session，因为请求结束了 session 就关了，而我的 producer 活得比请求久。producer 把 Agent 的事件逐条 publish 出去，SSE 连接只是一个**订阅者**，断开只是取消订阅，不影响执行。

然后我用一个 RunManager 来统一管这些 run 的生命周期，状态机是四个状态：`running`、`completed`、`failed`、`cancelled`。producer 正常跑完判 completed，中间看到 error 事件判 failed，被 cancel 判 cancelled。

还有一个细节我做的比较仔细：**首调度前就被 cancel 的兜底**。因为 asyncio 的 task 有可能在真正开始跑之前就被取消，这时候 producer 里的 try 根本没进去，handle 就会永远停在 running，所以我在 task 的 done callback 里补了一次判断。

后端这块一共是 71 个 REST 接口、15 张表。

`[claude_agent_sdk_service.py:1914-1916]`、`[run_manager.py:1-4, 61, 127-149, 203-228]`、`[conversations.py:552-566, 589-594, 611-639]`

## 2.2　长任务与断点恢复

**一句话主轴**：断线不丢进度，但内存不能无限涨。

**怎么讲：**

这块解决的是"用户网断了、或者刷新了，回来还能接着看"的问题。

我给每个事件打一个**单调递增的 seq**，然后写进一个环形缓冲。前端重连的时候带 `after_seq`，我就把缓冲区里 seq 比它大的事件按顺序回放给它，回放完再切成实时推送。实现上有个细节：**我是先注册订阅队列、再回放缓冲**，这样回放期间新产生的事件会同时进队列和缓冲，我最后按 seq 单调去重，保证**不丢也不重**。如果注册的时候 run 已经结束了，我再补一轮回放，防止快照和状态检查之间漏事件。

缓冲有两个上限：**1 万个事件，或者 8 MiB 字节**。超了就从最旧的一端淘汰，同时置一个 `replay_truncated` 标记，前端能读到这个标记，知道回放不完整了。如果**单个事件本身就超预算**，我的处理是把缓冲直接清空、全部走实时——不能让它卡死在淘汰循环里。

然后还有一个"慢消费者"的问题。SSE 是推流，如果某个客户端网络特别慢，排水跟不上，事件在服务端队列里会越堆越多。我设了**单个订阅者队列上限 2000**，到了就往它的队列里投一个结束哨兵、把这个订阅摘掉，表现就是连接断开，客户端会走重连路径、从回放缓冲把缺的补回来。**这是主动降级，不是无限堆积。**

最后是并发保护：**同一个对话同时只允许一个活跃 run**，第二次提交会被拒绝。为什么？因为 SDK 那层是 session resume，两个 run 同时操作同一个 session 会冲突。

`[run_manager.py:35-36, 38-40, 81-86, 90-101, 153-199]`、`[conversations.py:658-688]`

**⚠️ 必须主动交代的边界：**

1. **"并发提交被拒绝"具体返回什么码？**
   答：这里有个已知缺陷，我要如实说。设计意图是返回 409，但实现上 `RunActiveError` 是直接继承 `Exception` 的，没继承 `HTTPException` 或我们的 `AppException`；而抛异常的那一行在能转 409 的那个 `except` 块的**覆盖范围之外**——那个 except 包住的是函数调用，但 `run_manager.start()` 是在被调函数内部、在它自己 try 之前抛的。所以异常会冒泡到全局异常处理器，**实际返回 500**。代码注释还写着 409，注释和实现不一致，这是个应该修掉的缺陷。
   → 所以我在简历里只写"并发提交直接拒绝"，**没有写状态码**。

2. **队列上限 2000 覆盖全部链路吗？**
   答：不覆盖。它只覆盖 RunManager 这条通道。项目里还有一个更早的 EventBus，它的队列是**无上限**的，FileWatcher 和 SDK 的 stderr 回调还走它。这个我也知道是待改的地方。

## 2.3　工具权限与沙箱安全

**一句话主轴**：三层防护——授权收口、命令拦截、路径约束，再加容器。

**怎么讲：**

这块是我做得最细的地方，因为它关系到 Agent 会不会把环境搞坏。

**第一层，授权收口。** Agent 的每一次工具调用都要过我一个统一的回调。这里有个刻意的取舍：**我不用 `allowed_tools` 白名单**。原因是 `allowed_tools` 里的工具会**绕过回调直接放行**，那就等于权限管不住了。所以除了三个用来派生子 agent 的工具必须放行，其余全部走回调，一个一个判。

**第二层，危险命令拦截。** 我写了 **30 条正则**，分几类：递归强制删除、强制删除、往系统路径写、权限提升（sudo、su、chmod 777、chown root）、写设备（dd of=/dev/）、fork bomb、进程级破坏（killall、pkill、kill -9 1、shutdown、reboot）、磁盘格式化（mkfs）。命令长度上限 4000 字符。

不过这里我要讲清楚一件事：我**只拦真正危险的操作**，不拦 `pip install`、`python`、`cd`、`curl` 这些——因为 Agent 要靠这些去干活，拦了就废了。

**第三层，路径校验。** 这里有个我觉得挺有意思的坑。校验的逻辑是判断目标路径是不是在工作区根目录之下，但**顺序很关键**：必须**先**对工作区根做 `realpath` 得到解析后的 base，**再**用这个 base 去 join 相对路径，最后再 realpath 完整路径。

为什么不能反过来？因为工作区根**可能包含软链接组件**——比如 Docker 挂载点。如果我先拼接再 realpath，当目标文件**还没创建**的时候，`abspath` 会保留未解析的前缀，跟解析后的 base 前缀就对不上了，结果**合法路径被误判成越界**。这个是我踩出来的。

判断式就是解析后的路径等于 base，或者以 base 加路径分隔符开头。另外我拒绝以 `~` 开头的路径，绝对路径统一**重写成工作区内的相对路径**，防止它穿透到宿主机根目录。

**然后才是容器。** Linux 下我用 Docker 沙箱，容器参数是：`cap_drop=["ALL"]` 丢掉所有 Linux capabilities、`security_opt=["no-new-privileges"]`、内存限制 512M、CPU 配额 100000（等于 1 个核）、用宿主机的 uid/gid 以**非 root** 身份跑、工作区 bind mount 到容器里的 `/workspace`。容器有复用和回收机制，空闲超时回收加 LRU 淘汰，应用启停时挂回收器。镜像是一个预装了 pandas、numpy、matplotlib、python-docx 这些包的 python:3.11-slim。

`[claude_agent_sdk_service.py:2051-2133, 2216-2242]`、`[tools/security.py:34-74, 94, 201-278, 338-365]`、`[docker_shell_backend.py:405-423]`

**⚠️ 必须主动交代的三个边界：**

1. **危险命令拦截是什么性质？**
   答：坦白说它是**文本黑名单**，只能作为辅助控制，**不能替代容器隔离**。我们的安全报告里明确写了要专门测管道、重定向、命令替换、编码、PowerShell / CMD、通过 Python / Node / Java 间接执行、符号链接、后台进程、工作区外路径这些绕过手段。所以我在简历里只说"30 条正则拦截"，**没有暗示它等于安全沙箱**。

2. **沙箱实际跑起来验证过吗？**
   答：**没有。** 容器这部分的代码是真实实现，不是桩，但我们的开发环境是 Windows，Windows 走的是本地执行器，只在 Shell 层做了 `cd` 越界拦截，**根本不建容器**。所以"实际跑通"我不能说。

3. **gVisor 是不是你的隔离方案？**
   答：这里要说得准确：**gVisor 是可配置项，不是既成事实。** 配置里的默认值确实是 `runsc`，但函数签名和工厂传参的默认值反而是 `runc`，实际生效值取决于环境变量。所以我的表述是"运行时按 `SANDBOX_DOCKER_RUNTIME` 配置为 gVisor"，我**不敢说"已经跑在 gVisor 上"**。
   另外我也**没有写 read-only 根文件系统和网络隔离**——这两项在我们代码里是**零命中**的，只出现在文档里，所以我不能写进简历。

## 2.4　技能体系与产出物归因

**一句话主轴**：技能是可安装的资产，所以要校验和审核；产出物要能溯源到具体 run。

**怎么讲：**

**先讲技能。** 我们的技能包是一个 zip，里面**必须包含 `SKILL.md`**，`SKILL.md` 长度上限 60000 字符，它的 name 和 description 我用正则从 YAML front matter 里解析出来。

因为技能包是用户上传、还会被别的用户安装，所以上传侧我做了六层校验：

1. zip 完整性校验；
2. **拒绝符号链接**——看一眼 zip 条目 external_attr 里的文件模式位是不是软链接；
3. **拒绝路径穿越**（Zip Slip）——规范化每条路径，拒绝绝对路径、`~` 开头、含 `.` 或 `..` 段、首段带盘符的；
4. **拒绝重复文件**，而且是大小写不敏感地去重；
5. **解压总大小上限**，防 zip 炸弹；
6. **文件数上限**，另外每条都还要过扩展名白名单和单文件大小校验，而且是**按声明大小和实际读出来的字节各校验一次**。

**然后是双轨。** 我们有两套技能体系，是**两套独立的模型、服务和接口**：一套是**项目级技能**，落在项目的 `skills/` 目录；另一套是**注册中心**，相当于技能集市，有 12 个接口——提审、上传文档、审核通过、驳回、安装、浏览（只列已审核的）、管理端列表、我的发布、查版本、详情、下载、删除。

审核状态机是 `pending / approved / rejected`，**未审核通过不允许安装**，这是硬门禁，写在安装逻辑里。每次上传算一个 sha256 校验和，版本用 `skill_name + version` 组合，可以查一个技能的全部版本。

**再讲产出物归因**，这块我觉得是这个项目比较有意思的设计。

Agent 写文件有**两条路径**，我不能只处理一条：

- **Write / Edit / MultiEdit / NotebookEdit** 这几个工具，我能从工具入参的 `file_path` 直接拿到路径，所以把它们收集成一个**白名单集合**，FileWatcher 只对白名单里的路径建产出物。这样能过滤掉用户自己上传的文件、或者其他并发 run 写的文件。
- **Bash 这条路没有 `file_path` 参数**，它可能 `python x.py` 生成十个文件，我怎么知道是哪些？我的做法是**执行前后各拍一张快照**：把工作区所有相对路径和它的 `mtime_ns` 记下来，执行完再拍一张，取差集——**新增的文件**加上**被覆盖的文件**，拿这个差集去补建产出物。

还有一个坑：SDK 的 Write 工具用的是**原子写**——先写临时文件、再重命名到目标文件。重命名触发的是 `on_moved` 事件，**不是 `on_created`**，所以必须单独处理 `on_moved`，而且要用正则区分这个到底是 SDK 的临时文件（临时文件名有个 `.tmp.<数字>.<十六进制>` 的模式）还是用户手动重命名。

最后产出物落库要关联到具体的 `run_id` 和 `file_id`，而且建之前要查重——因为消费循环和批量建产出物之间可能有竞态，会重复建，所以加了一道"终极去重"查询。

**另外讲一下磁盘同步。** Agent 会直接往磁盘写文件、绕过 API，所以磁盘和数据库一定会不一致。我的处理是**读时同步**：有请求来读的时候才做同步，而且同一个项目有 **TTL 节流**和一个 **per-project 锁**，保证同一时刻只有一个同步在跑。同步的时候如果发现文件在磁盘上没了，就**软删**文件记录，同时把关联的 Artifact 也软删掉——不然对话流里的产出物卡片点下载会 404。

`[myskill_service.py:288-340, 342-362, 379-380, 420]`、`[skill_registry_service.py:408-411, 540]`、`[file_watcher.py:59-68, 482-485, 496-545, 561-579]`、`[claude_agent_sdk_service.py:1080-1082, 1317-1330, 1487-1503]`、`[disk_sync_service.py:1-10, 137-167, 240-247, 302]`

**⚠️ 必须交代：**

## 2.5　六阶段流水线（方案设计 + 交互原型）

**一句话主轴**：这条我**先自己划界**——设计是我参与的，原型是我写的，后端没有落地。

**怎么讲：**

这条我分两块说，**先说清楚边界，免得误会**：

**第一块，方案设计与技术选型。** 我参与设计了「AI 访谈 → 业务流程分析 → 业务需求分析 → 原型设计 → 数据库设计 → 低代码生成」这六个阶段的流水线。

它最核心的设计是**产出物串联**：上一步的产出物就是下一步的输入上下文。原型里对应的就是三个函数——取上一步产出物、保存本步产出物、取此前所有已完成步骤的产出物。每个阶段有自己的状态：未开始、进行中、已完成。

还有一个关键的技术决策：**复用既有的 SDK / RunManager / FileWatcher 链路，本体和实体实例改由技能包文件和产物 YAML 来承载**，所以设计结论是**零新增数据表**。这个结论是设计文档里明确的，不是我们只做了设计——而是**设计上就是不需要加表**。

**第二块，交互原型。** 这里我要说得非常明确：这是一套**纯前端的高保真交互原型**，Vue 3 CDN 加 Tailwind，**数据存在浏览器 localStorage，推理是本地 mock，没有任何真实的后端服务和模型调用**。整个原型里没有一处 `fetch`、`XMLHttpRequest` 或 `axios`，回复文本是关键词路由的模板字符串。

原型里我做了三件我觉得有点技术含量的事：

## 3.1　混合检索（核心攻坚）

**一句话主轴**：现象 → 根因 → 修复 → 代价，四段讲完。

**怎么讲：**

这个问题的现象是：我在测试问答里问"智能吸顶灯"，而 `table.csv` 里**明确有**这条设备记录，但系统就是查不出来。

我先怀疑是分块问题，后来定位到根因在**检索**：当时我**只用稠密向量做语义检索**。"智能吸顶灯"的语义向量，跟"门窗传感器""智能灯带"这类设备的向量**意外地更接近**，所以它被排到前面去了。**纯语义检索缺的是关键词精确匹配能力**——它知道"都是智能家居设备"，但不知道"吸顶灯"这三个字必须出现。

修复方式是：让 BGE-M3 在**一次前向里同时输出稠密向量和稀疏向量**。稀疏向量相当于 BM25 那种词权重的效果，负责精确匹配。然后两路**各取 2 倍候选**，用 **RRF 融合**，RRF 的常数 **k=60**。

实测结果是这样的：
- 精确查询"智能吸顶灯"：Dense、Sparse、Hybrid 三种方式 Top-1 都正确；
- 类目查询"照明设备"：Dense 的第 1 名是"智能灯带"，Sparse 的第 1 名是"智能筒灯"——**单路 Top-3 各漏 1 条**；**混合检索的 Top-3 把 3 条正确结果全收齐了**。

我还主动记录了代价：**检索时间增加约 30% 到 50%**（因为要跑两路检索），**存储增加约 10% 到 20%**（稀疏向量本身很稀疏）。我认为对于"查得出来"这个正确性问题，这个代价是可以接受的。

`[core/vector_store.py:126-152, 167-215]`、`[docs/hybrid-search-summary.md:5-11, 96-104, 128-132]`

**追问预备：**

- **为什么要用 RRF，不直接加权求和？**
  答：因为 dense 和 sparse 的分数**不在一个量纲上**——dense 是余弦相似度（0 到 1），sparse 是词权重的重叠和，数值范围完全不同，直接加权得先做归一化，而 RRF 只用到**排名**、不用到分数，所以不需要调参，也不用担心量纲。代价是丢掉了"第一名领先多少"这个信息。

- **k=60 是怎么定的？**
  答：这是 RRF 论文里的常用默认值，我没有针对自己的数据调过它，所以我在简历里把它写成参数，而不是写成"我调出来的最优值"。

- **你的召回率是多少？**
  答：我要如实说：**我没有做标准评测集**，用的是 2 条查询的定性对比，结论是"混合检索 Top-3 收齐了单路漏掉的结果"。我简历里如果出现 `MIRACL nDCG@10 稠密 69.2 / 稀疏 53.9`，那是 **BGE-M3 模型本身公开评测的成绩**，是我做**选型**的依据，不是我自己系统的实测指标。

## 3.2　嵌入选型与两段式检索

**一句话主轴**：选型有依据、检索分两段、底层能降级。

**怎么讲：**

**先说选型。** 我对比过 bge-large-zh 这些方案，最后选了 **BGE-M3**。选它的核心理由是：它**一次前向就能同时拿到稠密和稀疏两种向量**。如果我用别的 dense 模型，要再做混合检索就得额外引入一套稀疏检索的模型或索引，链路会变复杂。它的公开评测成绩是 MIRACL nDCG@10 稠密 69.2、稀疏 53.9，这是我的选型参考。

**第二段式检索。** 我的检索管线是四步：
1. 把 query 编码成稠密加稀疏；
2. 走混合检索召回 **20** 个候选；
3. 用 **Cross-Encoder 重排模型**（bge-reranker-v2-m3）把这 20 个精排到 **5** 个——因为双塔模型是 query 和 document 分开编码、精度不如交叉编码器，但交叉编码器太慢不能对全库跑，所以只能当精排用；
4. 回取父块上下文、算置信度。

重排模型这里我做了一个降级：**如果模型加载失败，我返回保持原序的结果**，而不是直接报错——宁可效果差一点，也不能让整条链路挂掉。

**底层降级。** 向量库走三级降级：**Milvus Server → Milvus Lite（本地文件）→ NumPy 内存库**。这样做是为了让系统既能在服务器上跑，也能在一台笔记本上直接启动。

`[core/embedder.py:75-101]`、`[core/reranker.py:53-83]`、`[core/retriever.py:41-124]`、`[config.py:49-61]`、`[core/vector_store.py:264-286]`

**⚠️ 必须主动交代：**

- **问：你生产上用的哪条路径？**
  答：这里有个**重要边界我必须说**：代码注释里明确写了 **Milvus 对稀疏向量支持不佳**，所以我那个稠密加稀疏的混合检索，**实际只在 NumPy 内存兜底层生效**；走 Milvus 的时候是**纯稠密检索**。这不是我漏了，是 Milvus Lite 这条路径的限制，要修得上 Milvus Server 的原生混合检索。

- **问：置信度怎么算的？**
  答：`0.6 × 最高分 + 0.4 × 平均分`，阈值 0.3，标签分 `very_low / low / medium / high` 四档。这是个经验公式，不是校准过的概率。

## 3.3　解析与分块

**一句话主轴**：入口要够宽（格式和编码），切法要按文档类型分，表格要特殊处理。

**怎么讲：**

**解析这边**支持 6 种格式：pdf、docx、csv、txt、md、doc，分别用 PyMuPDF 和 python-docx。企业文档最烦的是编码，所以我的文本读取是：先用 `chardet` 探测，然后把探测结果和一批候选编码依次尝试，候选里有 `gb18030`、`gbk`、`big5`、`cp936`。单文件上传上限 100 MB。

**分块这边**我定义了 **10 种策略**，按文档类型分派：朴素、通用、书籍、论文、简历、表格、问答、智能、父子、递归。

其中两个是我们重点用的：

- **父子分块**：子块 **512 token**、overlap 64；父块 **1536 token**、overlap 0。**用子块去检索**——因为块小、语义集中、向量更准；**命中之后回取它所属的父块**作为给模型的上下文。这样做是为了解决"检索准了、但上下文被切断"的矛盾。
- **表格分块**：**CSV 走特殊处理**——每行**独立成一个块**，而且**每个块里都注入表头**，因为单独一行数据是"SH001; 智能吸顶灯; 照明设备; Zigbee; 12; 299"，没有列名，模型不知道 12 是什么。Markdown 表格则是按整表提取成块，没有拆到行。

`[core/document_parser.py:34, 248-273]`、`[core/chunker.py:14, 156-163, 415-437, 764-794]`、`[core/retriever.py:96-99]`、`[config.py:45, 65-67]`

**追问预备：**

- **问：为什么 512 / 1536 这两个数？**
  答：子块 512 是常见的中文段落量级，保证语义集中；父块取 1536，也就是 3 个子块左右，够放下一段完整的上下文。overlap 只在子块上给 64，父块给 0——因为父块是给模型读的上下文，重复内容没意义。

- **问：10 种分块策略都要自己写吗？**
  答：有一个递归切分器作为底座，其他策略是在它之上做结构化的切法。比如智能分块是按标题和段落结构切、问答分块是按问答对切、表格按行切。

## 3.4　切分质量优化

**一句话主轴**：不是拍脑袋调参，是被召回问题**反向推动**的。

**怎么讲：**

这条不是我自己想优化就优化的，是**被前面的召回问题反向推出来的**。

我在排查"表里明明有却查不出来"的时候，用**召回分数和重排分数分布**去反推，发现两类切分问题：

第一类是**智能分块产生了大量过小分块**——一个独立的小标题就是一个块，8 个 token，这种块几乎没有任何语义，检索到它也没用。

第二类是**表格分块把 20 多行数据全塞进了 1 到 2 个块里**，导致一条记录被埋在中间，按记录检索根本命中不了。

于是我做了两个改动：
1. 给智能分块加了 `min_chunk_size=50`，并且**自动把过小的章节往后合并**；
因此我改了表格分块——**CSV 改成按行切、每行带表头**；Markdown 表格我保留了整表一块，没有拆到行。

效果是：
- 智能分块：分块数 **20 → 11**（−45%），过小分块 **12 → 5**（−58%），最小块 **8 → 31 token**（+287%），平均块长 **+80%**；
- 表格分块：**2 → 30 块**（CSV 场景），数据行不再被切断，每行都能独立召回。

`[docs/chunking-optimization-results.md:80-104]`、`[core/chunker.py:193-196]`

**⚠️ 主动交代：**
- 这个优化是**单文档前后对比**（一个 `intelligent.md`、一个 `table.csv`），不是跨数据集评测。所以我讲的时候会说清楚是"针对这两类文档的切分质量指标"，不会把它说成普遍提升。
- 优化完**仍然有 5 个小于 50 token 的块**，它们是真的独立短章节。文档里也写了下一步是把 `min_chunk_size` 提到 100。

## 3.5　链路可观测与流式问答

| 命令黑名单够安全吗 | 不够，文本黑名单只能辅助，不能替代容器隔离，管道/重定向/命令替换等都可绕过 |
| 并发提交返回什么 | ⚠️ 设计想返 409，实际因异常类型和控制流问题会返 **500**，注释与实现不符，是待修缺陷 |
| 支持多 worker 吗 | 不支持，EventBus / RunManager / client 池都是单进程内存态 |
| 队列 2000 覆盖全链路吗 | 不覆盖，只覆盖 RunManager；旧 EventBus 队列无上限仍在用 |
| 技能包有安全扫描吗 | ⚠️ 没有，scan_status 是占位字段，无任何实现 |
| 六阶段落地了吗 | ⚠️ 没有，设计文档自陈未做代码改动；`poc-*` 技能名与 `data/poc_skills/` 零命中 |
| 61 实体 380 属性是线上数据吗 | 不是，是设计文档里的规划规模，代码无对应本体文件 |
| 前端全是你写的吗 | 不是，基于开源 yudao-ui-admin-vue3 二次开发，自有部分在 `src/views/ap-agent/` |
| 有团队协作功能吗 | ⚠️ 前端有 TeamManagement 页面，后端无 team 表与接口，不算实现 |
| 13 类 SSE 事件 | 代码层面成立，但设计文档写的是 10 种（差 run_started / subagent_token / run_fatal），简历未写此数字 |

| 追问 | 回答要点 |
