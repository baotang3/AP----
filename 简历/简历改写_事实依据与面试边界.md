## 二、实习经历：每条的主轴与讲法

### 1. Agent 工作台后端（主轴：Agent 链路架构）

**简历写了**：FastAPI + Claude Agent SDK、ClaudeSDKClient 长连接、执行与 SSE 解耦、
RunManager 四态、71 个 REST 端点、15 张表。

**面试讲法**：先说清"为什么解耦"——Agent 一次 run 可能跑几分钟，如果挂在 HTTP 连接上，
用户一刷新就前功尽弃；所以让 producer 独立成 asyncio task、自建 DB session，
SSE 连接只是订阅者。

**证据**：`services/claude_agent_sdk_service.py:1914`、`services/run_manager.py:1-4`、
`api/conversations.py:589-594`、`main.py:197-210`。

**可深挖点（要预备）**：
- 71 是怎么数的？→ AST 统计 `backend/app` 下全部 `router.<method>` 装饰器；**用正则会数出 72**，
  多出的一条是 `core/database.py:93` 的 docstring 示例，不是真路由。方法分布 GET 36 / POST 22 /
  PUT 6 / DELETE 7。
- 15 张表 → `harness_*` 前缀，models 目录 17 个文件（15 表 + `__init__.py` + `base.py`）。

### 2. 长任务与断点恢复（主轴：流式可靠性）

**简历写了**：单调 seq、环形缓冲、1 万事件 / 8 MiB 双上限、after_seq 回放、
订阅者积压 2000 断流、并发提交拒绝。

**面试讲法**：这是一套"断线不丢进度"的设计。回放缓冲有上限，超了就置
`replay_truncated` 标记并降级为纯实时——**主动降级而不是无限吃内存**。
慢消费者不能拖垮 producer，所以积压到 2000 就丢哨兵断开，让它重连后从回放补齐。

**证据**：`run_manager.py:35-36`（10000 / 8MiB）、`:38-40`（2000）、`:90-95`（淘汰与标记）、
`:153-199`（subscribe_stream 回放 + seq 去重）、`conversations.py:677-688`（seq 注入 + ping 15s）。

**边界（必须主动说）**：
- 慢消费者上限 2000 **只覆盖 RunManager 通道**；另有一个旧 `EventBus`
  （`core/events.py:9`）队列**无上限**，FileWatcher 与 stderr 回调仍走它。
- 这套状态全在**单进程内存**里，**不支持多 worker**（`run_manager.py:15-17`、全局报告 `:253`）。

**不能说**：❌「并发提交返回 409」。实测 `RunActiveError` 继承 `Exception` 而非
`AppException`（`run_manager.py:46`），抛点 `conversations.py:587` 在转 409 的
`except`（`:552-566`）覆盖范围之外，会冒泡到全局处理器返回 **500**；代码注释写 409
但注释与实现不符。→ 简历只写"并发提交直接拒绝"，**不提状态码**。

### 3. 工具权限与沙箱安全（主轴：边界控制）

**简历写了**：can_use_tool 收口、不用 allowed_tools、30 条正则、realpath 顺序、Docker 参数。

**面试讲法**：
- 为什么不用 `allowed_tools`？→ 它会**绕过回调直接放行**，那样权限就管不住了
  （`claude_agent_sdk_service.py:2054-2055`）；只留 `Agent/Workflow/TaskOutput`
  三个委派类工具例外。
- 为什么 realpath 要在 join **之前**？→ 工作区根可能含 symlink（Docker 挂载点），
  若先拼接再 realpath，目标文件尚未创建时 `abspath` 会保留未解析前缀，与解析后的 base
  不匹配，**合法路径被误判越界**（`claude_agent_sdk_service.py:2216-2242`）。

**证据**：`tools/security.py:34-74`（30 条，分 9 类）、`:94`（命令长度上限 4000）、
`docker_shell_backend.py:405-423`（cap_drop=ALL / no-new-privileges / mem_limit=512m /
cpu_quota=100000 / 非 root / bind mount 到 /workspace）。

**边界（必须主动说）**：
- 危险命令拦截是**文本黑名单**，全局安全报告明确判为"只能作辅助控制，不能替代容器隔离"
  （`AP_Dev_Hub全景分析报告.md:369`）。**不要暗示它等于安全沙箱。**
- Docker 沙箱代码是真实实现，但**本次核查未实际启动容器验证**；当前 Windows 走
  `LocalSandboxExecutor`，不建容器（`sandbox_executor.py:149-151`）。
- gVisor 只是**配置默认值**（`config.py:237`），函数签名默认值反而是 `runc`
  （`docker_shell_backend.py:327`）。→ 简历写"运行时……运行"是安全的；**不要说"已跑在 gVisor 上"**。

**不能说**：❌ read-only 根文件系统、❌ 网络隔离。这两项在代码里**零命中**，只出现在文档。

## 三、RAG 项目：每条的主轴与讲法

### 1. 混合检索（主轴：缺陷定位并修复）—— 必被深挖

标准讲法（现象 → 根因 → 修复 → 代价）：
- **现象**：测试问答里 `table.csv` 明明有"智能吸顶灯"，却查不出来。
- **根因**：当时只用 Dense 向量；"智能吸顶灯"的语义向量与"门窗传感器"等设备意外更近，
  被排到前面——纯语义检索**缺关键词精确匹配**。
- **修复**：用 BGE-M3 单次前向同时产出稀疏向量，dense / sparse 各取 2 倍候选，
  按 RRF（k=60）融合（`core/vector_store.py:167-215`）。
- **实测**：精确查询「智能吸顶灯」三种方式 Top-1 都对；类目查询「照明设备」下
  Dense 第 1 是"智能灯带"、Sparse 第 1 是"智能筒灯"，**单路 Top-3 各漏 1 条，
  融合后 Top-3 收齐全部正确结果**（`docs/hybrid-search-summary.md:96-104`）。
- **代价（主动说）**：检索时间 **+30%~50%**、存储 **+10%~20%**（同文件 `:128-132`）。

### 2. 嵌入选型与两段式检索（主轴：选型有依据、有降级）

- BGE-M3 单次前向产出 1024 维稠密 + 稀疏（`core/embedder.py:75-87`）。
- MIRACL nDCG@10 稠密 69.2 / 稀疏 53.9 是 **BGE-M3 模型本身的公开评测**
  （BAAI arXiv:2402.03216 Table 5），是本项目的**选型依据**，不是本系统实测。
  → 被问"你的召回率多少"要如实说：**没有做标准评测集**，用的是 2 条查询的定性对比。
- Cross-Encoder 召回 20 → 精排 5（`config.py:60-61`、`core/reranker.py:53-83`）；
  重排模型不可用时降级为保序返回（`reranker.py:69-70`）。
- 三级降级 Milvus Server → Milvus Lite → NumPy 内存库（`vector_store.py:264-286`）。

**必须主动交代**：`vector_store.py:388` 注释写明 **Milvus 对稀疏向量支持不佳**，
所以**稀疏 + RRF 实际只在 NumPy 兜底层生效**；走 Milvus 时是纯稠密。
→ 被问"生产上用的哪条路径"要如实说。

### 3. 解析与分块（主轴：覆盖度 + 质量闭环）

- 6 种格式（pdf/docx/csv/txt/md/doc，`document_parser.py:34`）+ chardet 与
  gb18030/gbk/big5/cp936 编码回退（`:248-273`），单文件上限 100 MB（`config.py:45`）。
- 10 种分块策略（`chunker.py:14` 的 `ChunkMethod` + `:764-794` 工厂）；
  parent_child 子块 512 / overlap 64、父块 1536 / overlap 0（`chunker.py:156-163`），
  **子块检索、命中后回取父块补上下文**（`retriever.py:96-99`）。
- 表格分块：**CSV** 每行独立成块 + 每块注入表头（`chunker.py:415-437`）；
  Markdown 表格按整表提取，不拆行（`chunker.py:436-451`）。
- **质量闭环**（本条的加分点）：用召回与重排分数反推切分问题，再加 `min_chunk_size=50`
  与自动合并过小章节；结果 智能分块 20 → 11 块（−45%）、过小分块 12 → 5（−58%）、
  最小块 8 → 31 tokens（+287%）、平均块长 +80%；表格分块 2 → 30 块
  （`docs/chunking-optimization-results.md:98-104`、`:80-86`）。

**本版简历删掉的 RAG 要点（若被问到要能讲）**：
- 可观测：`POST /api/v1/kb/{id}/test-chat` 的 `metrics` 有 7 项（检索 / 重排 / 生成 / 总耗时、
  输入 / 输出 / 总 token），超过 50 字的查询自动 LLM 改写（`api/v1/document.py:585-601`、`:704-712`），
  命中 chunk_id 随答案落库可复盘（`chat.py:169-180`）。
  ⚠️ 该接口的 `rerank_score` 是**复制 `hybrid_score`** 的（`document.py:632-645`），
  `sparse_score`/`rerank_score` 默认 None，`rerank_time_ms` 不代表真实重排耗时——
  **不要拿它当重排指标**。
- 流式与路由：SSE 事件 `metadata`/`text_chunk`/`done` + `complete`/`error`；
  意图识别 5 类（text/chart/report/webpage/data_table）路由 4 个 Agent
  （`core/agent_router.py:21-26`、`agents/base_agent.py:29-43`），失败回落文本。
- LiteLLM 接入 10 类 provider 前缀（`core/llm_manager.py:19-32`）；
  MCP Server JSON-RPC over SSE，协议 2024-11-05，2 个工具
  `list_knowledge_bases` / `rag_chat`（`mcp/server.py:51`、`mcp/tools.py:116-168`）。
- 交付规模：46 个 Python 文件 / 4,594 行、37 个业务接口 + health、7 张表、
  18 个 .vue（8 组件 + 9 页面 + 根 App.vue）；docker-compose 编排 PostgreSQL / Redis / etcd /
  MinIO / Milvus v2.4.17 / backend / frontend 共 7 服务。

**三个不能说错的点**：
1. **没有单元测试框架**。全仓只有 3 个打印式验证脚本（`test_bge_m3_hybrid.py`、
   `test_hybrid_search.py`、`test-chunking-optimization.sh`），**无 pytest、无断言**。
   → 不要提"测试覆盖率"。
2. Milvus 路径只跑稠密（见上）。
3. `llm_manager.py:72` 是 `api_key = config.api_key_encrypted  # TODO: decrypt`——
   **模型 API Key 实际未加密存储**。不要声称实现了密钥加密。

## 四、被追问时的统一策略

1. **先划界再讲细节**：凡"设计/原型"就说清是设计或原型，凡"实现"就给文件位置。
2. **数字都能翻代码**：71 端点、15 表、13 类事件、30 条正则、10000/8MiB、2000、
   10 种分块、20→11、12→5、8→31、k=60、20→5、+30~50%、+10~20%——这些都在源码或
   仓库文档里可复现。
3. **主动交代代价与缺陷**：混合检索的性能代价、单进程内存态、文本黑名单局限、
   沙箱未实机验证、技能扫描是占位字段。这样说反而显得可信，也把追问提前封口。
4. **不主动扩大的表述**：不要把 1 万事件 / 8 MiB 说成吞吐或 SLA；不要把"资源归属链"
   说成已完成的全量多租户生产隔离；不要把 watchdog 说成无丢失强一致。
