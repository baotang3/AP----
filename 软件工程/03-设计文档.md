# 第一章 · 定位与目标

## 1.1 要做的事

`C:\dorbit_ai` 已实现一套完整的六阶段 POC 方法论。本次把它搬进 `AP_Hub`：

```
① AI 访谈 ──▶ ② 业务流程 ──▶ ③ 业务需求 ──▶ ④ 原型设计 ──▶ ⑤ 数据库设计 ──▶ ⑥ 低代码 POC
```

这六个阶段不是流水线的六道工序，而是**六件可以独立做的事**：

| 事实 | 含义 |
|---|---|
| **没有门禁** | 不需要等①做完才能做② |
| **没有强制顺序** | 可以直接做⑤数据库设计，完全跳过访谈 |
| **上游是可选输入** | 上游产物存在就注入，不存在就跳过，不报错 |

这条「阶段彼此独立」是整个设计的**前提**，后文所有取舍都建立在它之上。

## 1.2 为什么在 AP_Hub 上做，而不是新建服务

因为 `AP_Hub` **已经具备全部所需能力**，本次是把方法装载进去，不是再造一套平台。

| 六阶段需要什么 | `AP_Hub` 已有什么 | 标记 |
|---|---|---|
| 能调工具、能读写文件、能追问的执行引擎 | **Claude Agent SDK** 引擎（`[APP]services\claude_agent_sdk_service.py`） | `【原有】` |
| 阶段知识的装载 | 项目技能机制（`[APP]services\myskill_service.py`） | `【原有】` |
| 项目默认就带这套技能 | 项目创建时的预置目录钩子（`[APP]services\project_service.py`） | `【改动】` |
| 代码与脚本安全执行 | 沙箱（`[APP]services\docker_shell_backend.py`） | `【原有】` |
| 产物落盘与展示 | 文件监控自动登记 ＋ **四个画布**（`[UI]views\plugins\`） | `【原有】` |
| 断线不丢消息 | 执行总线（`[APP]services\run_manager.py`） | `【原有】` |
| 权限与多租户 | JWT / AAD ＋ `X-Workspace-Id` | `【原有】` |
| **阶段怎么串、进度怎么算** | **无** | **`【新增】`** |

**结论**：只有**编排**是新写的，其余全是既有的；方法论、本体、提示词是移植的。

## 1.3 核心思路：三条

### 思路一 · 复用 Claude Agent SDK，不另起执行引擎

六阶段本质上是「**带工具、会读写文件、会追问**」的 Agent 任务——SDK 已经把这些都做了。

而且既有 `/agent` 接口**本来就接受 `skill_id`**：

```python
# [APP]api\conversations.py（既有，本次不改）
async def agent_chat(conversation_id, payload: DirectChatRequest, ...):
    return _agent_chat_sse(conversation_id, payload.content, payload.model,
                           payload.skill_id, settings, llm, ...)

# [APP]services\claude_agent_sdk_service.py（既有，本次不改）
async def _resolve_system_prompt(self, skill_id, project_id) -> str:
    ...
    return default_prompt + skill_header + skill.md_content
```

**这两段既有代码就是「六阶段按 skill 封装」的全部执行侧实现。**

### 思路二 · 六阶段做成项目内置技能，不经技能集市

```
阶段的角色与工作流  →  SKILL.md      （追加到平台规则之后，成为该次执行的 system prompt）
阶段的参考资料      →  references/   （产出规范、本体数据）
阶段的确定性工作    →  scripts/      （结构校验）
```

**六个技能是项目的默认组成部分**，随项目创建自动装配——和既有的 `uploads/ skills/ results/` 三个预置目录同一时机、同一机制。**不发布到技能集市**：它们不是一个"可安装的能力包"，而是 POC 项目的固有组成部分。

阶段内部的「分析 → 抽取 → 提问」「分析 → 总结」**不再做成后端阶段**，退化为 `SKILL.md` 里的一段工作流说明，由模型在**同一次执行内**完成。后端因此不需要知道阶段内部有几小步。

### 思路三 · 产物即文件，按时间归一

```
模型写出文件  ──▶  文件监控自动登记  ──▶  产物记录
                                            │
                            同一路径多次生成 ──▶ 多条记录，按时间排
                                            │
                                最新的一条 ＝ 当前产物
```

**没有版本表，时间就是版本。** 既有 `[APP]services\artifact_service.py` 已经在做「按路径去重保留最新 ＋ 记录改写次数」。

## 1.4 边界

```
┌──────────────────────────┬──────────────────────────┬─────────────────────────┐
│                          │  【原有】AP_Hub 提供       │  【移植】来自 dorbit_ai   │
├──────────────────────────┼──────────────────────────┼─────────────────────────┤
│ 执行引擎                  │  Claude Agent SDK        │  —                      │
│ 阶段的知识                │  —                       │  SKILL.md · 本体         │
│                          │                          │  产出规范与提示词          │
│ 编排                      │  —                       │  —  【新增】编排层        │
│ 产物落地                  │  文件监控 ＋ 四个画布      │  —                      │
└──────────────────────────┴──────────────────────────┴─────────────────────────┘
```

### 明确不做

| 不做 | 原因 |
|---|---|
| 不新建平台或旁路服务 | `AP_Hub` 已具备全部所需能力 |
| 不把六个技能发布到技能集市 | 它们是项目固有组成部分，不是可安装的能力包 |
| 不自动串跑六个阶段 | 与「阶段彼此独立、无门禁」冲突 |
| 不移植生成器的 Python 代码 | 生成器本身就是调大模型的薄包装，套娃且会断掉流式输出 |
| 不新增数据库表、不新增数据库列 | 产物按时间归到既有产出物表；进度从产物推导 |
| 不改前端 | 复用既有对话、流式通道、四个画布 |
| 不改既有业务逻辑 | `/agent` 已支持 `skill_id` |
| 不自建分享 / 知识库 / 低代码 | 只留接口位置，见 3.7 |

## 1.5 交付节奏

| 期 | 内容 | 可验证结果 |
|---|---|---|
| **一期** | ② 业务流程技能包 ＋ 内置技能装配 ＋ 编排层 ＋ 端到端 | 新建项目自动带六个技能，对话里跑出产物，**画布渲染出来** |
| **二期** | ① 访谈（含本体）＋ ③④⑤ 技能包 | 六个阶段都能跑出产物 |
| **三期** | 第十章接口桩 | 全链路可用 |

> 一期选 ② 的理由：上游恒为空（正好验证阶段独立性）、产出规范已定位、产物是 YAML（正好验证画布契约）、不需要追问（交互最简单）。

## 2.3 六阶段 = 六个内置技能

**一个 POC 阶段 = 一个内置技能**，共六个。**项目创建时自动装配，不经技能集市。**

| # | 阶段 | 技能名 | 对齐既有词汇表 | 内部工作流（写在 `SKILL.md` 里） | 产物 | 画布 |
|---|---|---|---|---|---|---|
| ① | AI 访谈 | `poc-interview` | `productDesign` | 分析 → 抽取实体实例 → 下一个问题 | 实体实例 YAML | `ontology` |
| ② | 业务流程 | `poc-business-process` | `businessProcessMap` | 分析 → 总结 | 业务流程地图 YAML | `bpmMap` |
| ③ | 业务需求 | `poc-user-story` | `userStoryMap` | 分析 → 总结 | 用户故事地图 YAML | `storyMap` |
| ④ | 原型设计 | `poc-prototype` | `prototypeDesign` | 分析 → 总结 | 原型 HTML | — |
| ⑤ | 数据库设计 | `poc-database` | `databaseDesign` | 分析 → 总结（UML → 数据模型） | 数据模型 YAML | `dbDesign` |
| ⑥ | 低代码 POC | `poc-lowcode` | ❓ 无对应 | ❓ 待定 | ❓ 待定 | — （一期不启用） |

**装配落点**：项目工作空间的既有预置目录 `skills/` 下，六个子目录 `skills/poc-*/`，同时登记为项目技能（`harness_myskills`）。

> **「对齐既有词汇表」列不得改名**——这五个标识是既有前端与 `dorbit_ai` 共用的词汇，作为技能标签保留。

### ⚠️ 产物必须落在 `results/` 下（核对代码后修正）

平台的 system prompt（`[APP]prompts\claude_agent_sdk.md`）**强制**文件分级放置：

```
最终交付物  →  results/
中间文件    →  temp/          （且被排除，不登记为产物）
never write them in the workspace root
```

而 `_resolve_system_prompt` 注入技能时明确写着 **"on conflict, platform rules take precedence"**（冲突时平台规则优先）。

**所以产物目录不能自起一个 `poc/` 顶层目录**——模型有充分理由把它写进 `results/`，一旦如此，**按路径前缀推导阶段进度的机制会整体失效**。

**修正后的产物路径**：

|---|---|---|

## 2.4 为什么需要新增编排层与阶段定义

这是本次**唯一的新增架构**，所以说清理由。

### 编排层解决的是「做哪一步」，不是「怎么做」

SDK ＋ 技能机制提供的是**执行能力**：

| SDK ＋ 技能能回答 | SDK ＋ 技能**不能**回答 |
|---|---|
| 给定一段提示词和一个技能，怎么调工具 | 这个项目现在**该做哪一步** |
| 怎么读写文件、怎么写产物 | 这个阶段**做完了吗** |
| 怎么向用户追问 | 这个阶段对应**哪个技能** |
| 怎么流式输出 | 上游有什么、**在哪个文件** |
| 怎么在沙箱里跑脚本 | 上游变了，**哪些下游要重做** |

右边五问就是编排层的全部职责。

### 如果不做编排层，这五个答案只能落在两个地方

| 落点 | 后果 |
|---|---|
| **前端硬编码** | 前端要自己知道六阶段的名字、顺序、产物目录、上游关系、画布映射——与「**前端零改动**」直接冲突，且每加一个阶段都要改前端 |
| **`/agent` 接口硬编码** | 把平台的通用对话接口绑死到 POC 场景，影响工作台其他所有对话 |

### 所以编排层的价值是

**把「六阶段是什么」从执行引擎和前端里拿出来，用一份数据集中描述。** 它不驱动执行循环，只回答上面那五问。

规模很小：**约 400 行、4 个函数**。

### 为什么阶段定义要单独一个模块

| # | 理由 |
|---|---|
| 1 | 它是**纯数据**——六条记录（编号 / 名称 / 技能名 / 上游 / 产物目录 / 画布），不 import 数据库、不 import SDK，任何层都能安全引用 |
| 2 | 它被**三处**引用：编排层（推导进度）、接口层（返回清单）、技能包校验脚本（核对产物路径） |
| 3 | 若塞进 service，接口层为了拿一份**静态清单**就要依赖 service 的完整实现（含 DB 会话），还容易与编排层形成循环引用 |

> 上一版把它设计成 `constants/` **目录**，一个目录只放一个文件过重。**改为单文件 `[APP]constants.py`。**

```
    └── 装配六个内置技能                            ← 新增调用
          ├── 从 [APP]data\poc_skills\ 取技能包
          ├── 写进项目 skills/poc-*/ 目录（SKILL.md ＋ references/ ＋ scripts/）
          └── 登记为项目技能（harness_myskills）
    ▲ 幂等键：(project_id, 技能名)。已存在则整包跳过，不重复建
    ▲ 顺序硬依赖：必须在 create_preset_folders 之后
      —— 物化时按 icon_type == "my_skill" 找 skills 预置夹，
         找不到只打 warning 就静默返回：技能表有记录、磁盘没目录
      → 装配器必须自己断言目录已生成，不能依赖被调用方的静默行为
```

**装配为什么需要改 `myskill_service.py`**：

| 既有能力 | 能不能用 |
|---|---|
| `create()` → 建 `MySkill` 行 ＋ 物化 `skills/<名>/` ＋ **把 `SKILL.md` 写盘** | ✅ 直接用 |
| `materialize_skill_folder()` | ✅ 直接用 |
| `_ensure_skill_subfolder()` → 建 `references/` 子目录 | ❌ **私有方法** |
| `add_skill_file()` → `_create_file_record()` | ❌ **只 `db.add(File)`，不写磁盘** |

所以带 `references/ontology-*.yaml` 的技能包，**用现有公开 API 装不进磁盘**，模型 `Read` 不到本体 → ① 访谈技能直接失效。必须补一个公开方法把「建子目录 ＋ 写盘 ＋ 建记录」三件事做完（内部复用既有私有实现）。**这是第 5 处既有文件改动。**

**进度不建表、不改对话表** —— 完全从产物推导：

```
一个阶段「已完成」 ⟺ 项目下存在 relative_path 以该阶段 artifact_dir 开头的产物

not_started  该阶段目录下没有任何产物
running      该阶段绑定的对话存在活跃执行
done         存在该阶段产物
stale        存在该阶段产物，但有上游产物的 created_at 比它更新  ← 只标记，不自动重算
```

**启动接口不执行阶段**，只做三件事，然后前端用**既有的** `/agent` 发出去：

```
① 校验该阶段有对应技能（缺则先幂等装配，再校验）
② 组装阶段启动消息（上游产物路径清单 ＋ 产出要求）
③ 返回 { conversation_id, skill_id, content }
```

**验收**：新建项目后，`skills/` 下出现六个技能目录且项目技能列表有六条；重复执行装配不产生重复；一个新项目调用阶段清单，六个阶段全部「未开始」且**不报错**；直接做⑤跳过①②③④能正常出结果。

**为什么不搬生成器代码**：

| DSL 枚举含义未确认 | 中 | 校验保持宽松，只验顶层结构 |
| `yamlUtils.ts` 两版不等价 | 低 | 既有 159 行 vs 来源 214 行，移植前逐函数比对 |
| ⑥ 低代码阶段产物形态未定 | 低 | 一期不启用 |
