# 六阶段 POC 流水线 · 规则文档

> **版本**：v1.1（v1.0 为流水线规则；v1.1 补入配套模块规则、阶段交互模式规则、批次交付规则）
> **日期**：2026-09-18
> **状态**：已评审定稿
> **性质**：**规范性文件**。本文件中的「必须 / 不得」为强制约束，实现与评审均须逐条核对；「应该」为强烈建议，偏离需记录理由。
> **与其它文档的关系**：《01-需求文档》定义"做什么"，本文件定义"必须遵守什么"，二者共同约束《03-设计文档》。

---

## 1. 总则

### 1.1 规则的效力

| 级别 | 含义 | 偏离处理 |
|---|---|---|
| **必须 / 不得** | 强制约束 | 不可偏离；确需变更须先修改本文件 |
| **应该 / 不建议** | 强烈建议 | 可偏离，但需在设计文档中记录理由与影响 |
| **可以** | 允许 | 由设计决定 |

### 1.2 规则编号

`R-<域>-<序号>`。域：`ARCH` 架构、`DATA` 数据、`ART` 产出物、`STAGE` 阶段、`CTX` 上下文、`GEN` 生成、`SEC` 安全、`ENG` 工程、`DOC` 文档。

## 2. 架构规则（ARCH）

### 2.1 落点与边界

| 编号 | 规则 |
|---|---|
| **R-ARCH-01** | **必须**在 `C:\AP-dorbit-ai\AP_Hub` 内实现。后端落点 `ap_agent`（FastAPI），前端落点 `ap_agent_ui`。 |
| **R-ARCH-02** | **不得**修改 `C:\AP-dorbit-ai\ap-poc-agent` 目录下的任何文件。该目录是实现蓝图与需求基线，只读。 |
| **R-ARCH-03** | **不得**以 `C:\dorbit_ai` 的三个仓库为运行依赖。它们仅作为能力参考与提示词资产来源；本能力的实现必须在 AP_Hub 内自足。 |
| **R-ARCH-04** | **不得**在 AP_Hub 中引入 OWL / RDF / Turtle 技术栈（含 `rdflib`）。结构化约束一律采用 JSON Schema。 |
| **R-ARCH-05** | 本阶段**不得**引入对 Java 网关（`dorbit-api`）的依赖。阶段 6 的代码生成必须在 AP_Hub 内实现为确定性生成器。 |
| **R-ARCH-06** | 阶段 6 的代码生成器**必须**与编排层解耦：编排层只通过一个明确定义的输入契约（数据模型）与输出契约（生成清单 + 工程包）与之交互，以便将来替换为外部服务实现。 |

### 2.2 复用既有链路

| 编号 | 规则 |
|---|---|
| **R-ARCH-07** | 项目 / 工作空间 / 对话 / 消息 / 执行记录 / 文件 / 文件版本的既有表**必须**复用，不得重复建模。 |
| **R-ARCH-08** | `harness_artifacts` 表与 `FileWatcherService` 链路**必须保留不动**，继续作为"文件级变更登记"。新产出物模型通过文件 ID 与之汇合。 |
| **R-ARCH-09** | **不得**用新的产出物模型替代或架空 `harness_artifacts`。二者的职责区分必须保持：前者是"业务语义单元"，后者是"文件变更事实"。 |
| **R-ARCH-10** | 阶段提示词与阶段元数据**必须**外置为配置（JSON 文件或等价物），沿用既有 `prompts/subagents.json` 的范式：文件缺失时优雅降级并告警，不得导致服务启动失败。 |

### 2.3 分层

| 编号 | 规则 |
|---|---|
| **R-ARCH-11** | 必须遵守既有分层：路由层不得直接写数据库查询，须经服务层或仓储层。 |
| **R-ARCH-12** | 编排逻辑**必须**集中在独立模块中，不得散落在路由或提示词拼接代码里。 |

## 3. 数据模型规则（DATA）

### 3.1 通用

| 编号 | 规则 |
|---|---|
| **R-DATA-01** | 所有新增表**必须**继承既有 `Base` + `GUIDMixin` + `TimestampMixin`（需要软删除的用后者，纯快照表可以只用前两者）。 |
| **R-DATA-02** | 主键**必须**使用 32 位无连字符 GUID 字符串，与既有表保持一致。 |
| **R-DATA-03** | 新增字段**必须**可空或提供默认值，保证对既有数据与既有功能的**向后兼容**。 |
| **R-DATA-04** | 表名**必须**使用 `harness_` 前缀，与既有命名一致。 |
| **R-DATA-05** | 枚举取值**必须**在模型列的 `comment` 中列明，并在应用层以常量或枚举类型集中定义。 |

### 3.2 产出物表

| 编号 | 规则 |
|---|---|
| **R-DATA-06** | 产出物**必须**归属于项目（`project_id`），而非仅归属于对话。理由：产出物是项目资产，多个对话可共享。 |
| **R-DATA-07** | 产出物**必须**记录产出它的对话（可空）与执行记录（可空），用于溯源。 |
| **R-DATA-08** | 产出物**必须**包含 `stage_key` 与 `stage_order` 两列。`stage_order` 为冗余存储，用于排序与门禁判断，避免每次查询都去解析配置。 |
| **R-DATA-09** | 同一 `slug` 的"当前版本"唯一性**必须**由数据库约束或事务保证，**不得**仅依赖应用层逻辑。 |
| **R-DATA-10** | 版本号**必须**在同一 `slug` 内单调递增，不得跳号或复用。 |
| **R-DATA-11** | 版本快照表**必须**只增不改不删（除级联删除外），保证历史完整。 |
| **R-DATA-12** | 产出物**必须**记录内容哈希，用于判断"内容是否真的变化"。 |
| **R-DATA-13** | 长文本内容**应该**压缩存储；结构化内容（`content_json`）**必须**保留明文，以支持按字段查询与下游注入。 |

### 3.3 阶段定义

| 编号 | 规则 |
|---|---|
| **R-DATA-14** | 六个阶段的定义**不得**建表，**必须**以代码常量 + 配置文件承载。理由：阶段是固定不变的结构性事实，且其定义包含提示词等代码资产。 |
| **R-DATA-15** | 阶段的**进度状态不得**单独持久化，**必须**由该阶段的产出物派生。 |
| **R-DATA-16** | 「进行中」状态**可以**存在，但**不得**落库，只能体现在事件流与前端内存中。 |
| **R-DATA-17** | 行业模板**必须**建表（全局参考数据，不属任何项目），且**必须**可配置，不得硬编码。 |
| **R-DATA-18** | 模板的预填内容**必须**符合对应阶段的 JSON Schema；导入时应校验，不合规的模板不得启用。 |

### 3.4 对话表增量

| 编号 | 规则 |
|---|---|
| **R-DATA-19** | 对话**必须**新增「当前阶段」字段，作为阶段指针的唯一真源。 |
| **R-DATA-20** | 对话**必须**新增「已注入上下文指纹」字段，用于控制上游上下文的注入频率。 |
| **R-DATA-21** | 对话**应该**新增「进入当前阶段的时间」字段，用于停留时长埋点。 |

## 4. 产出物规则（ART）

### 4.1 双层结构

| 编号 | 规则 |
|---|---|
| **R-ART-01** | 产出物**必须**采用双层结构：结构化内容（`content_json` / `content_text`）为**语义层**，文件（`file_id`）为**渲染层**。 |
| **R-ART-02** | 语义层是**必需**的；渲染层是**可选**的。 |
| **R-ART-03** | 阶段间传递**必须**使用语义层。**不得**让下游 Agent 去读取和解析渲染层文件（如 PNG、PDF）来获取上游信息。 |
| **R-ART-04** | 渲染层文件**必须**通过既有文件表与文件存储承载，**不得**为产出物另建一套文件存储。 |

### 4.2 内容约束

| 编号 | 规则 |
|---|---|
| **R-ART-05** | 每个阶段的产出物结构**必须**由一份 JSON Schema 定义，该 Schema 是**唯一真源**。校验逻辑、文档、Agent 的输出约束**必须**全部由它导出，不得出现第二份定义。 |
| **R-ART-06** | 结构化产出物在保存前**必须**经 Schema 校验。 |
| **R-ART-07** | 校验失败时**必须**向 Agent 返回结构化错误（指明字段与期望），使其能够自行修正。**不得**静默丢弃或强行截断保存。 |
| **R-ART-08** | Schema 变更**必须**考虑对既有产出物的兼容：新增字段应可选，删除或改名需提供迁移路径。 |

### 4.3 版本

| 编号 | 规则 |
|---|---|
| **R-ART-09** | **所有生成历史必须完整保留**，任何位置（编排、清洗、存储）**不得**删除或覆盖历史版本。 |
| **R-ART-10** | 新版本产生时，同 `slug` 的原当前版本**必须**被标记为非当前（`is_active=False`），但**不得**删除。 |
| **R-ART-11** | 内容哈希未变化时**应该**不产生新版本，避免"重新生成但内容一致"造成历史噪音。 |
| **R-ART-12** | 版本记录**应该**包含变更说明；对由自然语言局部修改产生的新版本，变更说明**必须**指明"改了什么、其余保持不变"。 |
| **R-ART-13** | 回滚**必须**实现为"以历史版本内容创建新版本"，**不得**删除回滚点之后的版本。 |
| **R-ART-14** | 产出物**不得**存在"仅内存态"。任何被认定为完成的产出物**必须**已持久化。 |

### 4.4 生命周期

| 编号 | 规则 |
|---|---|
| **R-ART-15** | 产出物状态**必须**包含 `draft` / `generating` / `ready` / `failed`，且只有 `ready` 的产出物可被下游引用。 |
| **R-ART-16** | 「归档」**必须**实现为标记而非删除。归档的产出物不再被下游引用，但仍可查看与下载。 |
| **R-ART-17** | 上游产出物变更后，下游产出物**应该**被标记为"待重新生成"，但**不得**被自动删除或自动重算。 |
| **R-ART-18** | 「待重新生成」的标记**应该**在该产出物被重新生成后自动清除，不需用户手动清除。 |

## 5. 阶段执行规则（STAGE）

### 5.1 阶段指针

| 编号 | 规则 |
|---|---|
| **R-STAGE-01** | 阶段指针**必须**存放在对话上。产出物在项目上，阶段上下文在对话上，二者不得混淆。 |
| **R-STAGE-02** | 每个对话**必须**绑定且仅绑定一个当前阶段。 |
| **R-STAGE-03** | 阶段切换**必须**由显式的后端接口完成，且**必须**校验调用者对该对话的归属。 |
| **R-STAGE-04** | AI **不得**直接改变阶段。AI 只能在回复中给出建议入口，真正的切换由用户点击触发接口。 |
| **R-STAGE-05** | 阶段切换接口**必须**显式断开该对话的 Agent 客户端连接**并**清理客户端缓存，保证下一次调用走确定路径。理由：客户端缓存的复用判定与上下文恢复判定存在耦合，不显式清理会导致"有时重放、有时不重放"的不确定行为。 |
| **R-STAGE-06** | 阶段切换后，上游上下文指纹**必须**被重置，强制下次重新注入。 |

### 5.2 门禁

| 编号 | 规则 |
|---|---|
| **R-STAGE-07** | 「向前推进」**必须**受门禁约束：目标阶段之前的所有阶段**必须**均有就绪产出物。 |
| **R-STAGE-08** | 门禁不满足时，接口**必须**返回可识别的冲突响应，并列出缺失的阶段与产出物清单。 |
| **R-STAGE-09** | 「向后回退」**不得**受门禁约束。 |
| **R-STAGE-10** | 前端**必须**在门禁不满足时禁用"进入下一步"，并给出明确提示；但**不得**仅依赖前端校验，后端**必须**独立校验。 |

### 5.3 上下文恢复策略

| 编号 | 规则 |
|---|---|
| **R-STAGE-11** | 切换阶段时的默认行为**必须**是 `fresh`：**不重放**上一阶段的对话记录。 |
| **R-STAGE-12** | `fresh` 策略下，跨阶段信息传递**必须**完全依赖上游产出物的重新注入，**不得**依赖对话历史。 |
| **R-STAGE-13** | 该策略**必须**可配置，至少支持 `fresh` 与 `replay` 两种取值。 |
| **R-STAGE-14** | 策略取值**必须**显式配置，**不得**由运行时状态隐式决定。 |
| **R-STAGE-15** | 同一阶段内的连续对话**必须**保持上下文连续，不受该策略影响。 |

### 5.4 阶段定义内容

| 编号 | 规则 |
|---|---|
| **R-STAGE-16** | 阶段定义**必须**至少包含：阶段标识、序号、显示名称、对应的 Skill 名称、角色提示词、产出物 Schema 引用、该阶段可用操作、初始建议问题。 |
| **R-STAGE-17** | 阶段提示词**必须**以"追加"方式与平台基础系统提示词组合，**不得**整体替换。理由：平台基础提示词包含环境约束、文件分级、安全约束等行为规范，替换会导致行为漂移。 |
| **R-STAGE-18** | 阶段提示词**必须**沿用平台既有的输出语言跟随规则（跟随用户输入语言），不得硬编码单一语言。 |
| **R-STAGE-19** | 阶段可用的操作**必须**与阶段绑定，前端按当前阶段动态派发；**不得**像原型那样把所有阶段的操作混在一起全部显示。 |

### 5.5 阶段交互模式

| 编号 | 规则 |
|---|---|
| **R-STAGE-20** | **只有阶段 1（访谈）是访谈引导式**；阶段 2–6 **必须**为直接生成式，**不得**要求用户经过多轮对话才能得到产出物。 |
| **R-STAGE-21** | 阶段 2–5 的提示词**必须**以"生成器"形态编写（输入 → 结构化输出），**不得**沿用原型中为每阶段配多轮问答脚本的形态。原型做法属过度设计，不予采纳。 |
| **R-STAGE-22** | 阶段 6 **必须**不调用 LLM 推理，其输入完全来自阶段 5 的产出物。 |
| **R-STAGE-23** | 阶段 2–6 在缺少必要上游产出物时**必须**拒绝生成并给出明确提示，**不得**在信息不足时凭空生成。 |
| **R-STAGE-24** | 阶段 1–5 的生成**必须**流式呈现进度；阶段 6 的生成**必须**以步骤 / 进度形式呈现（**不得**使用 token 流式语义）。 |
| **R-STAGE-25** | 阶段 1 的提问顺序**必须**由结构化的问题清单驱动（来自阶段定义或行业模板），**不得**完全依赖模型自由发挥。 |
| **R-STAGE-26** | 阶段 2–5 生成后**可以**支持自然语言局部修改（只改目标项、其余不变），但该能力**不得**成为生成的前置条件。 |

## 6. 上下文传递规则（CTX）

| 编号 | 规则 |
|---|---|
| **R-CTX-01** | 阶段 N 执行时**必须**自动获取阶段 1..N-1 中所有 `is_active=True` 且状态为就绪的产出物内容。 |
| **R-CTX-02** | 上游上下文**必须**按阶段顺序组织后注入，使 Agent 能理解阶段间的先后与依赖。 |
| **R-CTX-03** | 上游上下文**必须**注入到 Agent 可见的输入中，**不得**要求 Agent 自行遍历文件系统去发现上游成果。 |
| **R-CTX-04** | 上游上下文**应该**注入在运行级输入而非系统提示词中。理由：系统提示词参与连接复用判定，上游内容变化会导致频繁重连。 |
| **R-CTX-05** | 上游上下文**不得**在每一轮对话中重复注入。**必须**通过内容指纹判断：指纹变化时才注入。 |
| **R-CTX-06** | 首次进入某阶段时**必须**注入；阶段切换后**必须**强制重新注入。 |
| **R-CTX-07** | 上游上下文**必须**设有 token 上限保护；超限时**必须**压缩或摘要，且关键结构化字段不得丢失。 |
| **R-CTX-08** | 获取上游上下文**应该**控制在单次数据库往返内完成。 |
| **R-CTX-09** | Agent 回复中**应该**体现已读取的上游产出物清单，便于用户确认传递生效。 |

## 7. 阶段 6 生成规则（GEN）

| 编号 | 规则 |
|---|---|
| **R-GEN-01** | 阶段 6 **必须**实现为确定性生成：给定同一份数据模型，**必须**产出同一份结果。**不得**由 LLM 自由创作代码。 |
| **R-GEN-02** | LLM 的职责在阶段 5 结束。阶段 6 **不得**依赖模型推理来决定生成什么文件。 |
| **R-GEN-03** | 生成器的输入契约**必须**与阶段 5 的产出物 Schema 完全一致（同一份定义）。 |
| **R-GEN-04** | 生成器的输出**必须**包含生成清单（文件路径 + 类型 + 来源），并随工程包一并保存。 |
| **R-GEN-05** | 数据模型中的类型标识若为数字枚举，**必须**在代码中以显式映射表定义，**不得**依赖隐式约定。 |
| **R-GEN-06** | 数据模型中的图形坐标**不得**由 AI 生成；**必须**由生成器或后端使用确定性布局算法计算。理由：AI 生成的坐标会出现重合与退化（历史上曾出现所有表沿一条 100px 斜线排布）。 |
| **R-GEN-07** | 生成模板资产**必须**集中管理、可版本化。 |
| **R-GEN-08** | 目标技术栈的版本取向**必须在设计阶段明确并保持一致**，不得出现"生成 Vue 2 而后端前端为 Vue 3"这类不一致。 |

## 8. 配套模块规则（AST / KB / AGT / MOD）

> 适用对象：资产库、知识管理、智能集市、预览面板、项目分享，以及与它们相关的模块边界约束。

### 8.1 模块边界（MOD）

| 编号 | 规则 |
|---|---|
| **R-MOD-01** | 六阶段流水线**必须**是核心能力，**不得**依赖资产库 / 知识库 / 集市中的任何一个才能工作。任一配套模块不可用时，流水线**必须**仍可完整执行。 |
| **R-MOD-02** | 配套模块**必须**通过《01-需求文档》第 8 章定义的接口消费流水线能力，**不得**直接读写流水线的存储表。 |
| **R-MOD-03** | 配套模块与流水线之间的耦合点**必须**可降级：知识库检索失败时**必须**降级为"无知识库上下文"并告警，**不得**中断 Agent 执行。 |
| **R-MOD-04** | 模块之间**不得**建立未在《01-需求文档》第 8 章定义的接口。新增跨模块依赖**必须**先补充需求文档。 |
| **R-MOD-05** | 配套模块的界面**必须**沿用工作台既有的抽屉 / 卡片视觉范式，**不得**为每个模块另造一套视觉语言。 |
| **R-MOD-06** | 预览内容**必须**来自真实文件，**不得**使用占位或伪造内容。不支持预览的类型**必须**给出明确提示与下载入口。 |
| **R-MOD-07** | 同一文件重复打开预览**必须**复用既有预览项，**不得**产生重复项。 |
| **R-MOD-08** | 项目分享**不得**使用写死的示例用户列表；分享对象**必须**来自真实用户体系。 |
| **R-MOD-09** | 被分享者的访问权限**必须**由分享关系驱动，并在产出物读取、阶段切换等路径上统一校验；**不得**只在前端隐藏入口。 |
| **R-MOD-10** | 取消分享后，被分享者的访问能力**必须**立即失效。 |

### 8.2 资产库（AST）

| 编号 | 规则 |
|---|---|
| **R-AST-01** | 资产库是**全局共享资源**，**不得**建模为项目私有数据；但**必须**记录创建者与可见范围。 |
| **R-AST-02** | 资产的「资源数量」**必须**由实际资源统计得出，**不得**存储为静态展示值。 |
| **R-AST-03** | 资产类别**必须**可配置，**不得**硬编码在代码或界面中。 |
| **R-AST-04** | 资产下载**必须**产出真实的打包文件；**不得**以提示或占位内容替代。 |
| **R-AST-05** | 资产被 Agent 引用时**必须**记录引用了哪个资产的哪个版本，保证产出物可追溯。 |

### 8.3 知识管理（KB）

| 编号 | 规则 |
|---|---|
| **R-KB-01** | 知识库及其文档**必须**持久化；**不得**存在"仅在界面上显示数量"的知识库。 |
| **R-KB-02** | 知识库的「文档数量」**必须**由实际文档统计得出。 |
| **R-KB-03** | 文档上传后**必须**记录解析状态；解析失败的文档**必须**可见且可重试，**不得**静默丢弃。 |
| **R-KB-04** | 文档被删除后，其切片与索引**必须**同步失效；检索结果中**不得**出现已删除文档的内容。 |
| **R-KB-05** | 知识库与项目**必须**通过显式关联关系绑定；检索**必须**限定在项目已关联的知识库范围内，**不得**跨项目检索。 |
| **R-KB-06** | 知识库检索结果注入 Agent 上下文时**必须**携带来源标识，使产出物可溯源。 |
| **R-KB-07** | 检索能力**必须**以独立的接口边界实现：本阶段 `IF-KB-06` **必须**以明确的"未启用"语义返回，**不得**引入向量库、嵌入模型或切片计算。**不得**以返回空结果冒充"检索无命中"——两者语义必须可区分。 |
| **R-KB-08** | 项目知识库的可见范围**必须**限定为项目成员；通用与行业知识库可为全局只读。 |
| **R-KB-09** | 知识库内容**不得**包含凭据、密钥或生产口令。 |
| **R-KB-10** | 编排层在收到检索"未启用"或失败时，**必须**降级为"无知识库上下文"并继续执行，**不得**中断 Agent 执行。 |

### 8.4 智能集市（AGT）

| 编号 | 规则 |
|---|---|
| **R-AGT-01** | 「立即使用」**必须**将智能体装配为**项目级可调用能力**，**不得**只做界面提示。装配结果**必须**在后续对话中真实可用。 |
| **R-AGT-02** | 装配操作**必须**幂等：同一项目重复装配同一智能体**不得**产生重复条目。 |
| **R-AGT-03** | 「使用次数」**必须**由实际调用统计得出，**不得**为静态展示值；统计口径**必须**明确并一致。 |
| **R-AGT-04** | 集市条目的分类**必须**可配置，**不得**硬编码。 |
| **R-AGT-05** | 集市条目与平台既有技能体系的关系**必须**明确定义（同一实体 / 两层结构），**不得**在两套体系间产生同名不同义的歧义。 |
| **R-AGT-06** | 智能体条目的上架、审核、下架属运营能力，普通用户**必须**只读。 |

## 9. 安全规则（SEC）

| 编号 | 规则 |
|---|---|
| **R-SEC-01** | 产出物的读、下载、删、回滚、归档**必须**校验归属链：当前用户 → 项目 → 产出物。 |
| **R-SEC-02** | 对话的阶段切换**必须**校验归属，**不得**允许操作他人对话。 |
| **R-SEC-03** | 阶段切换与产出物保存**应该**写审计记录。 |
| **R-SEC-04** | 模型输出**不得**直接作为 HTML 注入页面。结构化内容**必须**经安全渲染；需要富文本时**必须**经净化。理由：原型中存在直接注入模型输出的实现，属已知风险面。 |
| **R-SEC-05** | 模板为全局数据，普通用户**必须**只读；编辑能力**必须**限管理员。 |
| **R-SEC-06** | 产出物可能包含客户敏感信息，其渲染、预览、导出路径**必须**与平台既有安全策略一致，**不得**引入新的绕过路径。 |
| **R-SEC-07** | 模板内容**不得**包含真实客户数据。内置模板**必须**使用虚构示例数据。 |

## 10. 工程规则（ENG）

| 编号 | 规则 |
|---|---|
| **R-ENG-01** | 新增或修改的 Python 代码**必须**通过静态编译检查，并遵循既有代码风格与注释语言（中文注释 + 英文标识符）。 |
| **R-ENG-02** | 模块与函数**必须**有 docstring，说明职责与设计要点，沿用既有风格。 |
| **R-ENG-03** | 配置读取**必须**走既有配置机制，**不得**在业务代码中直接读取环境变量。 |
| **R-ENG-04** | **不得**提交任何凭据、密钥、生产口令到代码库。 |
| **R-ENG-05** | 数据库结构变更**必须**提供可重复执行（幂等）的迁移脚本，或明确说明依赖既有建表机制。 |
| **R-ENG-06** | 新增接口**必须**遵循既有响应结构与错误处理约定，**不得**为产出物单独发明一套响应包装。 |
| **R-ENG-07** | 新增事件**必须**纳入既有事件总线机制，事件命名**应该**与既有风格一致。 |
| **R-ENG-08** | 涉及并发写入产出物的路径**必须**考虑幂等与竞态；同一执行记录对同一路径的重复登记**必须**被去重。 |
| **R-ENG-09** | 本能力的改动**不得**降低 AP_Hub 既有功能的行为；回归范围**必须**包含文件、技能、对话、产出物面板。 |
| **R-ENG-10** | 交付**必须**依《01-需求文档》12.1 的批次划分：**第一批（六阶段流水线）必须能在第二批模块全部未实现的情况下独立完整验收**；第二批模块在第一批**只允许定义接口契约，不得实现功能**。 |
| **R-ENG-11** | 第一批的设计文档**必须**完整包含第二批模块的**接口设计**（《01-需求文档》第 8 章全部 `IF-*`）。目的：接口契约一次定清，第二批可独立并行开发，避免返工。**不得**把第二批接口留到第二批再设计。 |
| **R-ENG-12** | 第二批模块的接口设计**必须**做到：调用方（前端、编排层）按契约实现后，在第二批功能未实现期间**只依赖"未启用"语义降级**即可正常工作，**不得**要求调用方为"暂未实现"写临时分支。 |
