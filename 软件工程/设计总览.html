01整体架构：三层 + 一个数据底座

流水线由三层构成。编排层是新增的核心——它决定"现在该做什么、上游给了什么、产出物算不算完成"； 执行层复用既有 Agent 引擎；数据层复用既有表，只新增 3 张产出物表。

●编排层

回答三个问题：现在该做什么阶段？上游给了什么？这一步算完成了吗。

→ 阶段切换、门禁校验、上游上下文组装、失效传播

●阶段 6 生成器

唯一不经过 LLM 的环节。给定同一份数据模型，必得同一份结果。

→ LLM 的职责在阶段 5 结束

●第二批接口桩

本批只定义契约不实现，用统一的「未启用」语义让调用方无需临时分支。

→ 使第一批可独立完整验收

02六阶段流水线：收敛 → 展开

前 4 阶段产出面向人的业务描述，第 5 阶段把它们收敛成一份规范化数据模型，第 6 阶段由该模型机械展开成代码。 第 5 阶段的产出物是全链路唯一同时被「上游 AI 生成」与「下游机器消费」的契约。

为什么只有阶段 1 需要提问？ 原型 AI-chat.html 为每个阶段都配了多轮问答脚本， 但阶段 2–6 的信息源头是上游产出物而非用户。让它们反复提问既无必要，也会让"一键生成"变成"多轮才能出结果"。 因此阶段 2–5 的提示词写成生成器形态（输入 → 结构化输出），阶段 6 连模型都不调用。

03一次阶段推进的运行时形态

阶段切换是用户点击触发的显式动作，AI 不会自己跳阶段。整个链路里有三处设计得比较关键，图中已标出。

② 为什么必须显式断开连接
Agent 客户端的「是否复用」判定与「上下文是否恢复」判定是耦合的： 复用条件里包含"客户端缓存命中"。若不主动清理，切阶段后会出现用了新阶段的提示词、却静默丢掉了上下文的路径， 表现为"有时重放、有时不重放"的随机行为——极难排查。所以在阶段切换接口里显式断开并清缓存。
③④ 为什么注入放在运行级而非系统提示词
系统提示词参与客户端的复用判定（按内容哈希）。而上游产出物的变化频率远高于阶段切换—— 如果把上游内容塞进系统提示词，每次上游改动都会触发客户端重建。放在运行级输入里，客户端保持稳定。 再用内容指纹控制频率：指纹没变就不重复注入，避免每轮都塞一份重复的 JSON。

04产出物模型：语义与渲染分两层

这是全案的枢纽设计。同样的产出物，对机器和对人走两条完全不同的路径；两条路径的可靠性要求也完全不同。

为什么必须分两层

样本目录里 7 个真实产出物根本不是同一类东西，生成路径完全不同：

  • 访谈提纲 PDF —— 真文档（HTML 打印生成，13 页矢量）
  • 访谈总结 PNG —— 原型画布截图
  • 业务流程地图 PNG —— 画布截图（13452×3584）
  • 数据库设计图 PNG —— 外部设计器截图
  • 数据模型 DSL —— 该设计器的工程文件（JSON）
  • codegen.zip —— 真代码，78 个文件

更麻烦的是原型里还存在文件名与内容不符（PRD文档.docx 实际存的是数据库设计图）。

结论：渲染载体既不可统一生成、也不可信任为数据真源，必须与语义层解耦。

版本与失效
  • 生成历史完整保留，任何位置不得裁剪
  • 同一产出物任一时刻只有一个"当前版本"
  • 内容哈希未变则不产生新版本（避免噪音）
  • 回滚 = 以历史内容创建新版本，不删除后续版本
  • 上游变更 → 下游标记"待重新生成"，只标记不删不算
  • 标记随该产出物重新生成而自动清除

阶段进度从产出物派生，不单独存状态——因此永远不会出现"状态说完成但没有产出物"。

表结构职责划分

产出物主表

存"当前是什么"。下游取用的唯一入口，只查这一层。

产出物版本表

存"曾经是什么"。只增不改不删，供对比与回滚。

行业模板表

全局参考数据，不属任何项目。预填各阶段产出物内容。

既有文件产出物表

存"文件变更事实"。保留不动——与主表经文件 ID 汇合，互不替代。

两条链路的边界：编排层负责"业务语义"（哪个阶段、什么产出物、第几版）；文件监控负责"文件事实"（谁写了哪个文件）。 前者是新表，后者是既有链路。不要试图用一条链路涵盖两件事——这是原型和前身实现都容易走偏的地方。

06功能设计

按能力域组织。每个域标注交付批次与关键约束。

阶段编排 第一批

功能说明关键约束
阶段元数据6 个阶段的标识、序号、名称、图标、产出物定义、可用操作、初始建议问题配置驱动，缺失时优雅降级不阻断启动
阶段指针每个对话绑定一个当前阶段，默认第 1 阶段指针在对话上；产出物在项目上，二者不混
阶段切换用户点按钮触发，后端接口完成显式断开 Agent 连接 + 清缓存；AI 不得直接改阶段
前进门禁目标阶段之前所有阶段必须有就绪产出物不满足返回冲突 + 缺失清单；前后端都校验

失效传播上游变更 → 下游标记"待重新生成"只标记，不删除、不自动重算；随重生成自动清除
阶段进度各阶段是否就绪、产出物数量、最近更新从产出物派生，不存中间态

产出物管理 第一批

功能说明关键约束
保存产出物Agent 通过工具提交结构化结果Schema 校验；失败返回可修正错误让模型自修，不得静默丢弃
版本推进内容变化则产生新版本哈希未变不产新版本；旧版本转历史但不删

回滚回到指定历史版本实现为"以历史内容创建新版本"，不删回滚点之后的版本

上下文传递 第一批 流水线核心

功能说明关键约束
上游上下文获取取阶段 1..N-1 中"就绪且未归档"产出物的结构化内容单次查询走覆盖索引；按阶段顺序组织
内容指纹对上游内容算哈希，用于判断是否需要重新注入指纹没变 → 不重复注入（控制 token）
注入把上游内容作为本轮输入的一部分注入在运行级输入，不进系统提示词
预算保护上游过大时压缩关键结构化字段不得丢失
切换策略切阶段时是否重放上一阶段对话默认 fresh（不重放）+ 重新注入产出物；可配置
传递可见性回复中体现已读取哪些上游产出物便于用户确认传递生效
为什么默认不重放对话：阶段 2 的信息应来自阶段 1 的结构化产出物，而不是阶段 1 的原始聊天记录。 重放会带来三个问题——token 随阶段数累积、旧阶段的问答成为噪音、角色提示词切换后出现"身份混淆"。 结构化内容比原始对话更准，且不受对话轮次影响。

阶段 6 确定性生成 第一批

功能说明关键约束
输入校验必须拿到阶段 5 的数据模型缺失时拒绝生成并引导先完成阶段 5
类型映射数据模型的类型标识 → Java / TS / SQL 类型以显式映射表定义，不依赖隐式约定
命名派生表名 → 类名、文件名、包路径规则集中管理，可版本化
布局计算为数据模型计算画布坐标确定性算法；AI 不得生成坐标；结果不重合不共线
逐表生成每张表生成一套后端 + 前端 + SQL 文件审计字段自动继承，不重复生成

为什么这一阶段最可靠：它是纯函数式的——给定同一份数据模型，必得同一份字节级结果。 这意味着它可以被确定性测试（两次生成哈希一致 / 坐标不退化 / 前端产物确为 Vue 3）， 而前 5 个阶段的输出受模型随机性影响，只能靠 Schema 校验与人工确认。把不确定性收敛在第 5 阶段结束，是整条流水线最重要的可靠性设计。

07第二批模块：本批只定契约

4 个配套模块在原型中都有完整界面与数据形状。本批只完成接口设计（入参、出参、错误语义、降级行为）， 使第二批可独立并行开发、不返工。第一批必须能在第二批全未实现时独立完整验收。

资产库 第二批

可复用项目资产（组件/模板/规范/流程）的沉淀、检索、打包下载。内容以文件包形态存储。

  • 列表 / 增删改 / 资源清单 / 打包下载
  • 按阶段推荐：供编排层在生成时注入参考素材
  • 资源数量、下载包必须是真实统计与真实产物

原型中 3 个操作按钮连事件都没有，是纯空壳。

知识管理 第二批 检索不启用

为 Agent 提供领域知识与项目知识。本阶段数据模型、接口、界面全部实现，唯独检索能力不启用。

  • 知识库 CRUD（通用/行业/项目三级分类）
  • 文档上传与解析状态管理
  • 项目关联知识库（多对多）
  • 检索接口返回"未启用"——不引向量库、不引嵌入模型、不实现切片
"未启用"必须与"检索无命中"语义可区分。不得用返回空结果冒充无命中——否则调用方无法判断是功能没开还是真没有。
智能集市 第二批

智能体的发现与装配。沿用平台既有技能机制，不新造实体。

  • 条目列表 / 搜索 / 分类筛选
  • 「立即使用」= 装配为项目级可调用能力
  • 装配幂等（同项目重复装配不产生重复条目）
  • 使用次数由实际调用统计
原型里这个交互做对了一半：点击确实把智能体加进了工作空间的「技能」分组并预填了输入框， 但只加了个假条目、后续对话里并不可用。生产版必须做到装配后真实可调用。
项目分享 第二批

把项目分享给他人，并指定权限级别。

  • 分享对象来自真实用户体系（原型是 8 个写死的假用户）
  • 权限由分享关系驱动，统一在校验入口判定
  • 取消分享后立即失效
  • 「分享给我的」列表返回真实数据（原型恒为空态文案）

建议独立排期——涉及跨用户权限模型。

统一降级语义：让调用方不必写临时分支

{ "enabled": true, "items": [], "total": 0 }

前端显示空态；编排层同样跳过但记 debug 日志。

为什么强调这个区分：如果两种情况都返回空数组，调用方就无法区分"功能没开"和"确实没有"， 只能写成 if (items.length === 0) { /* 猜是哪种？ */ }——最后要么误报错误，要么被迫在第二批上线时改动第一批的代码。 前端通过一次能力查询拿到各模块开关，在渲染层决定是否显示入口，而不是在业务逻辑里散落判断。

08关键设计解释

这些是评审时最容易被问"为什么要这样"的地方。每条都对应一个具体的历史教训或技术约束。

为什么不改既有的文件产出物表

它在跑：文件监控服务盯着工作空间，文件一变就自动登记。改动它等于改动一条活跃链路。

而两者语义本就不同——新表管业务语义（哪个阶段、什么产出物、第几版）， 既有表管文件事实（谁写了哪个文件）。分开反而更清楚，经文件 ID 汇合即可。

为什么阶段定义不建表

六个阶段是固定不变的结构性事实，不是用户数据。而且其定义里包含提示词等代码资产， 放进数据库反而难以版本管理——前身实现走"脚本生成本体文件 → 导入库 → 重启服务"三步， 复杂度正来自把配置放进了库。

阶段进度也不单独存：从产出物派生既省一张表，又杜绝了"状态与实际不一致"。

为什么坐标不能交给 AI

历史上曾出现所有表沿一条 100px 斜线排布（Left=Top=n*100）——坐标由上游 AI/网关生成导致的退化排布。

改为后端确定性算法后，同一输入必得同一输出：可测、可复现、不会退化。而且坐标只是渲染信息，与生成内容无关。

为什么阶段 6 不用模型

给定同一份数据模型，需要的是可复现的代码而不是"每次略有不同"的创作。

把不确定性收敛在第 5 阶段结束，换来的是：阶段 6 可以做确定性测试、失败可归因、重复生成不产生噪音。

为什么提示词是"追加"而非"替换"

平台基础提示词里有环境约束、文件分级规范、安全约束、语言跟随规则等行为规范。

整体替换会导致行为漂移（比如中间文件写错目录、误用解释器）。所以阶段内容只作为专业角色与流程追加。

为什么要显式禁止旧技术栈

样本 codegen.zip 生成的是 Vue 2（index.vue + 选项式）， 而目标前端 ap_agent_ui 是 Vue 3。

这类"样本与目标不一致"如果不显式记录，实现者照着样本做就会产出无法接入的代码。 所以目标栈作为显式字段写进生成清单，而不只是靠约定。

为什么要有"待重新生成"而不是自动重算

用户改一个上游，下游全自动重算听起来很美，但成本不可控——一次访谈改动可能触发 4 个阶段、每次都要调模型。

标记 + 用户选择性重生成，把控制权交回用户，同时避免"改一个字就烧掉一整条流水线"。

为什么原型里的部分功能要"补"而不是"照抄"

原型有 3 处缺口：阶段 4/6 的产出物根本无法生成（截图里恒为 0 个文件）； 产物文件名与内容不符；产出物不持久化（刷新即清零）。

需求文档以产出物语义（阶段 + 标识 + 类别）而非文件名来定义，正是为了绕开这些坑。
