第一章 · 背景与项目定位#

1.1 业务背景#

C:\dorbit_ai 已经实现了一套完整的六阶段 POC 方法论：从需求访谈、业务流程分析，一直到数据模型设计与原型生成。

text
① AI 访谈  ──▶  ② 业务流程  ──▶  ③ 业务需求  ──▶  ④ 原型设计  ──▶  ⑤ 数据库设计  ──▶  ⑥ 低代码 POC

这六个阶段不是流水线的六道工序，而是六件可以独立做的事：

事实含义
没有门禁不需要等①做完才能做②
没有强制顺序可以直接做⑤数据库设计，完全跳过访谈
上游是可选输入上游产物存在就注入，不存在就跳过，不报错

这条「阶段彼此独立」是整个设计的结构性前提，后文所有取舍都建立在它之上。

1.2 项目定位#

本次要做的是给 AP_Hub 增加一套能力，不是新建一个平台。

AP_Hub 已经具备承载这套方法论所需的全部平台能力：对话与消息、工作空间与文件、沙箱执行、Claude Agent SDK 引擎、技能体系与技能集市、权限与多租户隔离、SSE 流式执行总线。

所以本次的定位可以一句话概括：

text
不在 AP_Hub 旁边再起一个服务，
而是把六阶段做成 AP_Hub 里的六个技能，让既有的 Agent 引擎去执行它们。

由此得出两个直接后果：

  1. dorbit_ai 那套服务不再需要运行。 移植完成后 AP_Hub 是唯一实现。
  2. 本次几乎不碰数据库、不碰前端、不改既有业务逻辑。 详见 2.6 与第六章。

1.3 三份输入素材#

素材角色对待方式
C:\AP-dorbit-ai\ap-poc-agent原型：定义六个阶段与每阶段产物的形态只读，作为功能与产物形态的需求来源
C:\AP-dorbit-ai\AP_Hub载体：平台骨架，含 Agent 引擎与技能体系在其上增量开发，既有代码尽量不动
C:\dorbit_ai被移植的源：方法论、提示词、本体数据搬进 AP_Hub，代码级搬运，不是 HTTP 调用

1.5 设计原则#

#原则说明
一阶段彼此独立六阶段无门禁、无强制顺序。任何阶段在任何上游缺失时都必须能单独跑通
二复用 Claude Agent SDK不另起执行引擎。六阶段就是 Agent 任务，SDK 已经会做工具调用、沙箱、追问、流式
三六阶段按技能封装一个 POC 阶段 = 一个技能。阶段的方法论写在 SKILL.md 里，分发走既有技能机制
四产物即文件，按时间归一阶段成果落在工作空间文件；文件监控自动登记为产物。不设版本表、不设快照，同一路径按时间保留最新
五上下文给路径，不给全文上游产物只把路径交给模型，由模型用 Read 按需读。不把上游产物全文拼进提示词
六前端不改复用既有对话、流式通道、四个画布、技能商城。前端仓库零改动
七既有业务逻辑不改复用既有 /agent 接口（它本来就接受 skill_id）。本次不修改任何既有业务逻辑
八本体是访谈的核心资产提问顺序与「还缺哪些属性」是访谈区别于通用聊天的根本，不可简化

1.6 术语约定#

本文后续统一使用以下术语，前五个容易混，先在这里定死。

术语含义回答的问题
本体一套领域知识清单「做需求访谈时，该问哪些东西」
实体清单里的一个类别「要问的其中一个东西是『付款条件』」
属性某个类别下要收集的信息项「『付款条件』要问付款周期、账期天数」
实体实例某个类别问到的一个具体答案「这个项目的付款条件是月结 30 天」
产物六阶段生成出来的文档「这个项目做出了哪些东西」
阶段POC 方法论里的一件独立的事，共六个「现在在做哪一步」
技能包一个阶段的完整封装（SKILL.md ＋ 参考资料 ＋ 脚本）「这一步的知识放在哪个文件里」

三组关系一句话说清：

text
本体  ──包含──▶  实体  ──包含──▶  属性
                    │
                    └──问到答案──▶  实体实例（带"还缺哪些属性"）

六个阶段  ──每个封装成──▶  一个技能包  ──装配到项目──▶  项目技能（MySkill）

一次阶段执行  ──模型写出──▶  产物文件  ──文件监控登记──▶  产出物记录（按时间保留最新）

产物没有版本表。 同一路径每次重新生成都会产生一条新的产出物记录，按 created_at 排序；最新的一条就是当前产物，旧记录仍然留在数据里可查。详见 7.2。

第三章 · 具体架构一：编排层（重新设计）#

3.1 为什么要重新设计#

旧设计把编排做成了「后端状态机」：后端持有能力清单、推进阶段指针、逐步执行、为每一步发事件。这套做法有一个绕不开的矛盾：

矛盾后果
后端决定跑哪几步、按固定顺序 —— 而 Agent 引擎是模型决定调用什么工具、几轮、何时停把顺序控制权交给模型，与「后端编排」直接冲突
后端要下发动态步骤清单 —— 而前端只认识固定的一组事件类型步骤清单下发不出去，只能做事件映射妥协
后端要自建「提问落库」机制 —— 而 SDK 已经有 AskUserQuestion同一件事两套机制，还要自定义事件名与字段
后端要把上游产物全文拼进提示词上游产物动辄上千行，token 爆炸、截断、失真

重新设计的思路：把「决定」和「执行」分开。

text
编排层决定：  现在该做哪个阶段、绑定哪个技能、告诉模型上游有什么
SDK 执行：   怎么做、调哪些工具、写哪些文件、要不要追问

编排层因此变成一个薄层：它不驱动执行循环，只在执行开始前把上下文准备好、在执行结束后从产物里读出结果。

【新增】 services/poc_orchestrator.py。它只做四件事，全部是读和算，不驱动执行循环。

3.4 阶段进度怎么推导#

不新增进度表、不给对话加阶段指针列。 进度是从产物推导出来的。

text
一个阶段"已完成"  ⟺  项目下存在 relative_path 以该阶段 artifact_dir 开头的产物

四种状态：

状态判定
not_started 未开始该阶段目录下没有任何产物
running 进行中该阶段绑定的对话存在活跃执行（查既有执行状态）
done 已完成存在该阶段产物
stale 上游已变更 ⚠️存在该阶段产物，但上游产物中有比它更新的

stale 用时间戳比较判定，只标记、不自动重算：

text
若 存在上游产物 p，满足 p.created_at > 本阶段产物.created_at   →  stale

这与「产物按时间归一」是同一套语义：时间就是版本。用户看到「上游已变更」，自行决定要不要重跑。

代价：进度推导每次要查一次项目的产物列表。产物量在单项目下是几十条量级，可接受；如将来需要，可在编排层加短周期缓存。

第四章 · 具体架构二：生成层（重新设计）#

4.1 为什么要重新设计#

dorbit_ai 的产物生成是 14 个 Python 模块，共 1,455 行。每个模块长一个样：

text

在旧设计里，这套东西是「移植对象」：把 14 个模块改写成异步、接上统一模型工厂、外面再套一层「统一分派抽象」。

在 SDK 模式下定格看这件事，结论反转了：

事实含义
这 14 个模块本身就是在调大模型它们是 LLM 调用的一层薄包装，不含业务算法
SDK 模式下模型自己就能写出产物文件再让模型用 Bash 去调一个「会调大模型的 Python 脚本」＝ 套娃
套娃会断掉流式链路脚本内部的 LLM 调用不经过执行总线，用户在对话里看不到生成过程
真正有价值的是提示词与输出结构约 1,302 行，在另一个文件里（configs/prompt_config.py）

所以生成层的重新设计是一句话：不移植代码，只移植提示词与产出结构。

生成层不再是一层 Python。它是技能包里的资产：

4.5 产物契约与校验#

路径契约 ⚠️#

阶段状态是按产物路径前缀推导的，所以「产物写到哪」是一个必须被保证的契约：

保障层措施
技能包SKILL.md 用约束条目写明确切输出路径，例如 poc/02-业务流程/业务流程地图.yaml
启动消息build_stage_prompt 在「产出要求」段落里再写一次目标路径
平台既有 system prompt 里已经有文件分级放置规则，要求产物放在项目目录而非根目录
校验技能包 scripts/validate_*.py 检查顶层结构；产物归错目录时前端能看到「产物列表为空」

⚠️ 残余风险：模型仍可能写错路径。缓解：进度推导里「路径前缀不匹配」的表现是「该阶段未完成」，属于可观测的失败而不是静默错误；一期首要验证项之一就是路径稳定性。

结构校验：宽松#

【新增】 校验脚本只做一件事：看顶层结构在不在。

text

为什么不用 subagent 做阶段编排#

理由说明
subagents.json 是模块级常量，进程启动时加载一次六个阶段子 agent 会注册到整个平台的每一个对话里，而六阶段只对 POC 项目有意义
子 agent 是「委派」，适合并行评审类任务六阶段是长任务、各自产出文件、需要用户交互，不是委派形态
阶段推进要用户控制委派给主 agent 等于把「现在做哪一步」交给模型，与阶段独立的既定需求冲突

既有 subagents.json 当前只有 pre-review / post-review 两个（退税工作底稿场景，14 行），本次不改它。

与「一次执行一条记录」的关系#

file_watcher.py 的去重规则是 (run_id, relative_path)：同一次执行内同一路径只登记一条；不同执行产生不同记录。

代价对策
⚠️ 内容没变也会产生一条新记录产生的是记录不是文件（File 内容被覆盖），存储开销可忽略；产物列表归并后用户只看到一条
