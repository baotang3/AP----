# 第一章 · 背景与项目定位

## 1.1 业务背景

`C:\dorbit_ai` 已经实现了一套完整的**六阶段 POC 方法论**：从需求访谈、业务流程分析，一直到数据模型设计与原型生成。

```
① AI 访谈  ──▶  ② 业务流程  ──▶  ③ 业务需求  ──▶  ④ 原型设计  ──▶  ⑤ 数据库设计  ──▶  ⑥ 低代码 POC
```

这六个阶段不是流水线的六道工序，而是**六件可以独立做的事**：

| 事实 | 含义 |
|---|---|
| **没有门禁** | 不需要等①做完才能做② |
| **没有强制顺序** | 可以直接做⑤数据库设计，完全跳过访谈 |
| **上游是可选输入** | 上游产物存在就注入，不存在就跳过，不报错 |

这条「阶段彼此独立」是整个设计的**结构性前提**，后文所有取舍都建立在它之上。

## 1.2 项目定位

**本次要做的是给 `AP_Hub` 增加一套能力，不是新建一个平台。**

`AP_Hub` 已经具备承载这套方法论所需的全部平台能力：对话与消息、工作空间与文件、沙箱执行、**Claude Agent SDK 引擎**、技能体系与技能集市、权限与多租户隔离、SSE 流式执行总线。

所以本次的定位可以一句话概括：

```
不在 AP_Hub 旁边再起一个服务，
而是把六阶段做成 AP_Hub 里的六个技能，让既有的 Agent 引擎去执行它们。
```

由此得出两个直接后果：

1. **`dorbit_ai` 那套服务不再需要运行。** 移植完成后 `AP_Hub` 是唯一实现。
2. **本次几乎不碰数据库、不碰前端、不改既有业务逻辑。** 详见 2.6 与第六章。

## 1.3 三份输入素材

| 素材 | 角色 | 对待方式 |
|---|---|---|
| `C:\AP-dorbit-ai\ap-poc-agent` | **原型**：定义六个阶段与每阶段产物的形态 | 只读，作为功能与产物形态的需求来源 |
| `C:\AP-dorbit-ai\AP_Hub` | **载体**：平台骨架，含 Agent 引擎与技能体系 | 在其上增量开发，既有代码尽量不动 |
| `C:\dorbit_ai` | **被移植的源**：方法论、提示词、本体数据 | 搬进 `AP_Hub`，**代码级搬运，不是 HTTP 调用** |

## 1.5 设计原则

| # | 原则 | 说明 |
|---|---|---|
| 一 | **阶段彼此独立** | 六阶段无门禁、无强制顺序。任何阶段在任何上游缺失时都必须能单独跑通 |
| 二 | **复用 Claude Agent SDK** | 不另起执行引擎。六阶段就是 Agent 任务，SDK 已经会做工具调用、沙箱、追问、流式 |
| 三 | **六阶段按技能封装** | 一个 POC 阶段 = 一个技能。阶段的方法论写在 `SKILL.md` 里，分发走既有技能机制 |
| 四 | **产物即文件，按时间归一** | 阶段成果落在工作空间文件；文件监控自动登记为产物。**不设版本表、不设快照**，同一路径按时间保留最新 |
| 五 | **上下文给路径，不给全文** | 上游产物只把**路径**交给模型，由模型用 `Read` 按需读。不把上游产物全文拼进提示词 |
| 六 | **前端不改** | 复用既有对话、流式通道、四个画布、技能商城。**前端仓库零改动** |
| 七 | **既有业务逻辑不改** | 复用既有 `/agent` 接口（它本来就接受 `skill_id`）。本次不修改任何既有业务逻辑 |
| 八 | **本体是访谈的核心资产** | 提问顺序与「还缺哪些属性」是访谈区别于通用聊天的根本，不可简化 |

## 1.6 术语约定

本文后续统一使用以下术语，前五个容易混，先在这里定死。

| 术语 | 含义 | 回答的问题 |
|---|---|---|
| **本体** | 一套领域知识清单 | 「做需求访谈时，**该问哪些东西**」 |
| **实体** | 清单里的一个类别 | 「要问的其中一个东西是『付款条件』」 |
| **属性** | 某个类别下要收集的信息项 | 「『付款条件』要问付款周期、账期天数」 |
| **实体实例** | 某个类别问到的一个具体答案 | 「这个项目的付款条件是月结 30 天」 |
| **产物** | 六阶段**生成出来的文档** | 「这个项目做出了哪些东西」 |
| **阶段** | POC 方法论里的一件独立的事，共六个 | 「现在在做哪一步」 |
| **技能包** | 一个阶段的完整封装（`SKILL.md` ＋ 参考资料 ＋ 脚本） | 「这一步的知识放在哪个文件里」 |

三组关系一句话说清：

```
本体  ──包含──▶  实体  ──包含──▶  属性
                    │
                    └──问到答案──▶  实体实例（带"还缺哪些属性"）

六个阶段  ──每个封装成──▶  一个技能包  ──装配到项目──▶  项目技能（MySkill）

一次阶段执行  ──模型写出──▶  产物文件  ──文件监控登记──▶  产出物记录（按时间保留最新）
```

> **产物没有版本表。** 同一路径每次重新生成都会产生一条新的产出物记录，按 `created_at` 排序；**最新的一条就是当前产物**，旧记录仍然留在数据里可查。详见 7.2。

## 2.2 分层结构与依赖方向

后端沿用既有的严格分层，**禁止跨层调用**：

```
API 路由层（app/api/）
    │  只做参数校验与依赖注入
    ▼
Schema 层（app/schemas/）        ← 出入参契约
    │
    ▼
Service 层（app/services/）      ← 核心逻辑；编排层在这一层
    │
    ▼
Model 层（app/models/）          ← ORM 与数据库操作
```

本次新增的部分**严格落在既有分层里**：

| 层 | 【新增】 | 说明 |
|---|---|---|
| 常量 | `constants/stages.py` | 六阶段定义，纯数据、无依赖 |
| Schema | `schemas/poc.py` | 阶段出入参 |
| Service | `services/poc_orchestrator.py` | 编排层 |
| API | `api/poc.py` | 三个阶段端点 |
| 资产 | `data/poc_skills/` | 六个技能包（不是 Python 模块） |
| 脚本 | `scripts/seed_poc_skills.py` | 技能包发布与装配 |

**没有新增 Model。** 这是本次设计的一个明确结论，理由见 7.2。

# 第三章 · 具体架构一：编排层（重新设计）

## 3.1 为什么要重新设计

旧设计把编排做成了「后端状态机」：后端持有能力清单、推进阶段指针、逐步执行、为每一步发事件。这套做法有一个绕不开的矛盾：

| 矛盾 | 后果 |
|---|---|
| 后端决定跑哪几步、按固定顺序 —— 而 Agent 引擎是**模型决定调用什么工具、几轮、何时停** | 把顺序控制权交给模型，与「后端编排」直接冲突 |
| 后端要下发动态步骤清单 —— 而前端只认识固定的一组事件类型 | 步骤清单下发不出去，只能做事件映射妥协 |
| 后端要自建「提问落库」机制 —— 而 SDK 已经有 `AskUserQuestion` | 同一件事两套机制，还要自定义事件名与字段 |
| 后端要把上游产物全文拼进提示词 | 上游产物动辄上千行，token 爆炸、截断、失真 |

**重新设计的思路：把「决定」和「执行」分开。**

```
编排层决定：  现在该做哪个阶段、绑定哪个技能、告诉模型上游有什么
SDK 执行：   怎么做、调哪些工具、写哪些文件、要不要追问
```

编排层因此变成一个**薄层**：它不驱动执行循环，只在执行开始前把上下文准备好、在执行结束后从产物里读出结果。

## 3.2 阶段定义

**【新增】** `constants/stages.py` —— 纯数据，无数据库依赖、无副作用。

```
StageDef
  ├── no            阶段编号 1..6
  ├── key           稳定标识（skill 名的一部分）
  ├── name          中文名
  ├── skill_name    技能名        poc-interview / poc-business-process / …
  ├── agent_code    对齐既有词汇表 productDesign / businessProcessMap / …
  ├── upstream      上游阶段编号列表（可为空）
  ├── artifact_dir  产物目录      poc/01-访谈/ · poc/02-业务流程/ · …
  ├── outputs       期望产物文件名与契约
  ├── canvas        对应画布      ontology / bpmMap / storyMap / dbDesign / —
  └── enabled       是否启用      ⑥ 一期为 false
```

六个阶段里 **② 的上游为空**（正好是最适合先做的一条，见 9.2）；**⑥ 一期不启用**。

`artifact_dir` 是整条链路的关键约定：**产物放在哪个目录，决定了它属于哪个阶段。**

## 3.3 编排层的职责

**【新增】** `services/poc_orchestrator.py`。它只做四件事，全部是**读**和**算**，不驱动执行循环。

| # | 职责 | 契约 |
|---|---|---|
| 一 | **阶段定义查询** | 返回六阶段清单与定义，供接口与前端使用 |
| 二 | **进度推导** | 从项目产物推导每个阶段的状态（见 3.4） |
| 三 | **Skill 绑定** | 按 `skill_name` 在项目技能里找 `MySkill.guid`；未装配返回 `None`（不抛异常） |
| 四 | **上下文组装** | 组装阶段启动消息（见 3.5） |

对外契约：

```
list_stages(project_id) -> list[StageState]
    六阶段清单 ＋ 每阶段的状态、产物列表、绑定的 skill_id

resolve_stage_skill(project_id, stage_no) -> str | None
    在项目技能里按 skill_name 查找；未装配返回 None

build_stage_prompt(project_id, stage_no) -> str
    组装阶段启动消息；契约：永不抛异常，上游缺失时只省略对应段落

derive_stage_state(artifacts, stage_def) -> StageState
    纯函数：按 relative_path 前缀把产物归属到阶段
```

**编排层不写数据库。** 它只读产物、读技能、算状态、拼文本。所有写操作都发生在 SDK 执行过程中，由既有的文件监控完成。

## 3.4 阶段进度怎么推导

**不新增进度表、不给对话加阶段指针列。** 进度是**从产物推导出来的**。

```
一个阶段"已完成"  ⟺  项目下存在 relative_path 以该阶段 artifact_dir 开头的产物
```

四种状态：

| 状态 | 判定 |
|---|---|
| `not_started` 未开始 | 该阶段目录下没有任何产物 |
| `running` 进行中 | 该阶段绑定的对话存在活跃执行（查既有执行状态） |
| `done` 已完成 | 存在该阶段产物 |
| `stale` 上游已变更 ⚠️ | 存在该阶段产物，**但上游产物中有比它更新的** |

`stale` 用**时间戳比较**判定，只标记、不自动重算：

```
若 存在上游产物 p，满足 p.created_at > 本阶段产物.created_at   →  stale
```

这与「产物按时间归一」是同一套语义：**时间就是版本**。用户看到「上游已变更」，自行决定要不要重跑。

> **代价**：进度推导每次要查一次项目的产物列表。产物量在单项目下是几十条量级，可接受；如将来需要，可在编排层加短周期缓存。

## 3.5 上游上下文注入

这是编排层最值得说的一处重新设计。

**旧做法**：把上游产物全文读出来，拼进提示词。

**新做法**：**只给路径，让模型自己 `Read`。**

```
阶段启动消息（由 build_stage_prompt 组装）
  ├── 阶段目标          "完成本项目的业务流程分析，产出业务流程地图"
  ├── 产出要求          期望文件路径 poc/02-业务流程/业务流程地图.yaml ＋ 结构说明
  ├── 上游产物清单 ★    路径 ＋ 标题 ＋ 大小，不给内容
  │      poc/01-访谈/实体实例.yaml            （实体实例）
  │      poc/03-业务需求/用户故事地图.yaml     （若已存在）
  └── 参考资料          技能包 references/ 下的资产路径
```

**为什么这样更好**：

| 好处 | 说明 |
|---|---|
| 上下文交给引擎 | 模型按需读、按需裁剪，不必把几千行塞进 system prompt |
| 上游缺失天然可跳过 | 清单为空就少一段，**不需要任何「上游存在性」判断逻辑** |
| 技能包资产同一条路 | 本体 61 实体 / 380 属性同样以文件形式给路径，不进提示词 |
| 与 `SKILL.md` 不冲突 | 文件分级放置本来就是平台规则的一部分，模型知道怎么读 |

**契约**：`build_stage_prompt` **永不抛异常**。上游有任何问题——不存在、为空、路径失效——对应段落省略，执行继续。这样「任意阶段单独可跑」是**结构上的保证**，不是靠调用方小心。

## 3.6 访谈问答的衔接

① AI 访谈是六个阶段里唯一需要多轮交互的。**不需要自建机制**。

```
模型判断需要向用户提问
    │
    ▼  AskUserQuestion 工具
question_pending 事件  ──▶  前端弹出提问卡片      【原有 ★ 前端已实现】
    │
    ▼  POST /api/conversations/{id}/answer-question 【原有 ★】
用户回答落库，SDK 会话被唤醒继续
    │
    ▼
模型把答案写进  poc/01-访谈/实体实例.yaml
    │
    ▼
FileWatcher 登记为产物 → 本体画布读取渲染         【原有 ★】
```

| 旧设计要做的事 | 现在 |
|---|---|
| 自定义 `question_chunk` 事件 | 不需要，用 `question_pending` |
| 自定义 `question_complete` 事件 | 不需要，答案经 `/answer-question` 回灌 |
| 对话表加 `step3_question_text` 字段 | **不需要** |
| 后端维护「待回答问题」内存态 | 不需要，SDK 与既有追问机制已具备 |
| 前端为「第三阶段双重语义」做分支 | **不需要**，前端不知道有「阶段」这回事 |

> **一个刻意的一致**：① 的「下一个问题」和其余阶段的「一份产物」，在系统里形态完全不同——一个是对话里的追问，一个是工作空间里的文件。旧设计为了统一它们付出了自定义事件与自定义字段的代价；新设计**不为它们做统一**，各自用最自然的既有机制。

## 3.7 并发、中断与续跑

全部复用既有执行总线 `run_manager.py`（263 行），**不新增任何并发控制**：

| 能力 | 既有实现 | 本次怎么用 |
|---|---|---|
| 每对话单活跃执行 | `RunActiveError`，冲突返回 409 | 同一阶段不会跑两次 |
| 单调序号 | 每个事件带 `seq` | 前端可检测丢包 |
| 回放缓冲 | 事件数与字节数双上限 | 断线重连补发 |
| 订阅流 | 先回放、后实时 | 前端 `sseClient.js` 已支持 `after_seq` 续传 |

**中断**：用户停止 → 既有 `POST /api/conversations/{id}/stop`。已写入的产物文件**保留**（它们已经落盘并被登记），中断不会毁掉已完成的产物。

**续跑**：重新发起该阶段即可。因为阶段的输入是「上游产物路径」，重跑等价于再执行一次，不依赖上一次的任何内存状态。

## 3.8 编排层的边界

明确**不做**的事，与做的事同样重要：

| 不做 | 原因 |
|---|---|
| 不自动串跑六个阶段 | 「阶段彼此独立、无门禁」是既定需求；自动串跑等于把独立变成流水线 |
| 不设门禁、不校验阶段顺序 | 同上 |
| 不驱动执行循环 | 执行循环属于 SDK；编排层只在开始前准备、结束后读取 |
| 不自建事件协议 | 既有事件已足够，且前端只认识既有那几种 |
| 不写数据库 | 所有持久化由既有服务和文件监控完成 |
| 不实现生成器的 Python 分派 | 生成层不存在 Python 生成器，见第四章 |
| 不判断「上游内容是否够用」 | 那是模型的事；上游缺失就让模型自己去要 |

# 第四章 · 具体架构二：生成层（重新设计）

## 4.1 为什么要重新设计

`dorbit_ai` 的产物生成是 **14 个 Python 模块，共 1,455 行**。每个模块长一个样：

```
取提示词  →  LLMChain 包一层  →  流式调用大模型  →  剥离代码围栏  →  返回文本
```

在旧设计里，这套东西是「移植对象」：把 14 个模块改写成异步、接上统一模型工厂、外面再套一层「统一分派抽象」。

**在 SDK 模式下定格看这件事，结论反转了**：

| 事实 | 含义 |
|---|---|
| 这 14 个模块**本身就是在调大模型** | 它们是 LLM 调用的一层薄包装，不含业务算法 |
| SDK 模式下**模型自己就能写出产物文件** | 再让模型用 `Bash` 去调一个「会调大模型的 Python 脚本」＝ 套娃 |
| 套娃会**断掉流式链路** | 脚本内部的 LLM 调用不经过执行总线，用户在对话里看不到生成过程 |
| 真正有价值的是**提示词与输出结构** | 约 1,302 行，**在另一个文件里**（`configs/prompt_config.py`） |

**所以生成层的重新设计是一句话：不移植代码，只移植提示词与产出结构。**

## 4.2 生成层的形态

生成层**不再是一层 Python**。它是**技能包里的资产**：

```
生成层 ＝  SKILL.md（怎么做 + 产出什么）
         ＋ references/（提示词资产、产出结构规范、本体数据）
         ＋ scripts/（仅确定性工作的脚本，不调大模型）
```

| 部分 | 形态 | 谁执行 |
|---|---|---|
| 阶段工作流 | `SKILL.md` 里的一段说明 | 模型按说明执行 |
| 产出结构规范 | `references/*-spec.md`（移植自生成提示词） | 模型读取并遵循 |
| 本体数据 | `references/ontology/*.yaml` | 模型按需 `Read` |
| 结构校验 | `scripts/validate_*.py` | 模型用 `Bash` 调用 |

**对旧设计的删除**：

| 旧设计的东西 | 现在 |
|---|---|
| 14 个生成器模块（1,455 行） | **不移植** |
| 生成器接口抽象 `gateway/base.py` | **不需要**——没有 Python 生成器可分派 |
| 14 个生成器实现 | **不需要** |
| LangChain 依赖替换表 | **不需要**——不再有 LangChain 调用 |
| 「业务代码零硬编码生成器」约束 | **自动满足**——代码里根本没有生成器 |
| 「自动续跑生成」机制 | **不需要**——产物就是这次执行写出的文件，不是执行之后的第二次调用 |

> **「自动续跑」为什么消失了**：旧设计里阶段先产出「需求描述」文本，再触发第二次生成调用把它变成产物。SDK 模式下，`SKILL.md` 直接要求模型**产出产物文件本身**，中间物不存在，第二次调用也就不存在。这也顺带消掉了幂等、并发保护、失败不毁旧版本这三条约束。

## 4.3 生成模块逐条处置

`[QINWEN]server\chat\dorbit_ai\` 共 15 个文件、1,455 行（14 个生成模块 ＋ 一个空 `__init__.py`）。逐条处置：

| 原模块 | 行数 | 产出 | 处置 |
|---|---|---|---|

## 4.5 产物契约与校验

### 路径契约 ⚠️

阶段状态是**按产物路径前缀推导**的，所以「产物写到哪」是一个**必须被保证的契约**：

| 保障层 | 措施 |
|---|---|
| 技能包 | `SKILL.md` 用约束条目写明确切输出路径，例如 `poc/02-业务流程/业务流程地图.yaml` |
| 启动消息 | `build_stage_prompt` 在「产出要求」段落里再写一次目标路径 |
| 平台 | 既有 system prompt 里已经有文件分级放置规则，要求产物放在项目目录而非根目录 |
| 校验 | 技能包 `scripts/validate_*.py` 检查顶层结构；产物归错目录时前端能看到「产物列表为空」 |

⚠️ **残余风险**：模型仍可能写错路径。**缓解**：进度推导里「路径前缀不匹配」的表现是「该阶段未完成」，属于**可观测的失败**而不是静默错误；一期首要验证项之一就是路径稳定性。

### 结构校验：宽松

**【新增】** 校验脚本只做一件事：**看顶层结构在不在**。

```
校验通过条件（示例：业务流程地图）
  ├── 是合法 YAML
  ├── 顶层存在约定的键
  └── 内容非空
```

**明确不校验**：

| 不校验 | 原因 |
|---|---|
| 枚举字段的取值 | 部分 DSL 数字枚举含义尚未确认（见 A.2） |
| 引用完整性 | 跨表字段的关联关系解析成本高，且模型出错时表现明显 |
| 内容质量 | 不是脚本能判断的 |

> **未确认项不得猜测。** 校验保持宽松，脚本里对未确认枚举标注 `❓ 未确认`。

### 必须剥离代码围栏

产物 YAML 若带 ``` 围栏，**画布会渲染成空白**。这条要求在 `SKILL.md` 的约束段落里明确写出，是一期必须验证的一项。

## 4.6 生成层的边界

| 不做 | 原因 |
|---|---|
| 不移植 14 个生成器模块的 Python 代码 | 套娃；且会断掉流式链路 |
| 不保留生成器接口抽象 | 没有需要分派的实现 |
| 不引入第二套大模型调用方式 | 生成由 SDK 内的模型完成，不需要额外调用 |

| 不实现 ⑥ 低代码代码生成 | 移植源与后端都没有实现，能力在外部平台（见 10.4） |

## 5.3 本体与实体实例

### 本体是什么

访谈之所以不是通用聊天，是因为它知道该问哪些实体、每个实体有哪些属性、哪些还没问到。这套知识以**本体**形式存在，共五套，合计 **61 个实体、380 个属性**：

| 场景 | 实体 | 属性 | 用途 |
|---|---|---|---|
| `general` | 15 | 87 | 通用需求访谈（当前在用） |
| `agent_database_design` | 16 | 103 | 数据库设计专用 |
| `finance_shared` | 11 | 67 | 财务共享行业 |
| `procurement` | 9 | 58 | 采购行业 |
| `ma_implementation` | 10 | 65 | 并购实施行业 |

### 本次的存放方式 ⚠️

| 数据 | 存哪 | 为什么 |
|---|---|---|
| **本体定义** | 技能包资产 `references/ontology/*.yaml` | 静态定义；模型按需 `Read`，不进提示词、不入库 |
| **实体实例** | 产物 `poc/01-访谈/实体实例.yaml` | 本体画布本来就是**读 YAML 文件**渲染，不是读接口 |

## 5.4 产物

### 产物的口径

```
一次阶段执行  ──模型写出──▶  产物文件  ──文件监控登记──▶  产出物记录
                                                            │
                                          同一路径多次生成 ──▶ 多条记录，按时间排
                                                            │
                                              最新的一条 ＝ 当前产物
```

**没有版本表，时间就是版本。**

| 概念 | 说明 |
|---|---|
| 产物文件 | 工作空间里真实存在的文件，画布直接读它 |
| 产物记录 | `harness_artifacts` 表里的一行，记录路径、类型、所属执行、时间 |
| 当前产物 | 同一路径下 `created_at` 最新的一条 |
| 历史 | 同一路径的历史记录**保留可查**，不做删除 |
| 改写次数 | 既有 `ArtifactService` 已计算 `run_count`，供前端显示「已更新」 |

| 编号 | 功能 | 归属 | 说明 |
|---|---|---|---|
| 4.1 | 产物自动登记 | `【原有】` | `file_watcher.py` 监听写文件，自动建 File ＋ Artifact |
| 4.2 | **按路径归并保留最新** | `【原有】` | `artifact_service.py` 已实现，与「按时间归一」的要求一致 |
| 4.3 | 改写次数标记 | `【原有】` | 既有 `run_count` |
| 4.4 | 按阶段归属 | `【新增】` | 编排层按 `relative_path` 前缀把产物归属到阶段 |
| 4.5 | 产物下载 | `【原有】` | 产物关联 `file_id`，复用既有下载通道 |
| 4.6 | 产物预览 | `【原有】` | 复用既有预览通道与四个画布 |
| 4.7 | 上游失效标记 | `【新增】` | 时间比较，只标记不重算 |

### 验收标准

1. 同一阶段连续跑两次，产物列表里该路径**只有一条**，且 `run_count` 为 2。
2. 两次内容不同，**当前产物是后一次的**；历史记录仍在数据库里可查。
3. 跨对话验证：对话 A 产出业务流程产物后，对话 B 做数据库设计时，产物清单里能看到它。
4. 上游产物更新后，依赖它的下游标记为「上游已变更」，**内容未被改动**。
5. 工作空间里的产物文件与产物列表里的路径一致。

## 6.5 直接复用：Claude Agent SDK 与 Skill 机制

这是本次设计的**核心复用点**，值得单独列清。

### 引擎侧已经具备的能力

| 能力 | 既有实现位置 | 本次怎么用 |

| 换技能重建会话 | 客户端按 `prompt_hash` 缓存 | 阶段之间互不污染 |

### 为什么不用 subagent 做阶段编排

| 理由 | 说明 |
|---|---|
| `subagents.json` 是**模块级常量**，进程启动时加载一次 | 六个阶段子 agent 会注册到**整个平台的每一个对话**里，而六阶段只对 POC 项目有意义 |
| 子 agent 是「委派」，适合**并行评审**类任务 | 六阶段是长任务、各自产出文件、需要用户交互，不是委派形态 |
| 阶段推进要用户控制 | 委派给主 agent 等于把「现在做哪一步」交给模型，与阶段独立的既定需求冲突 |

> 既有 `subagents.json` 当前只有 `pre-review` / `post-review` 两个（退税工作底稿场景，14 行），**本次不改它**。

### 为什么六个技能不必各带 Python

`MySkill` 有 `py_content` / `tools.py` 字段，但本次不使用：

| 理由 | 说明 |

## 7.2 产物：按时间归一（不设版本表）

### 结论

**不新增产物版本表、不新增快照表、不新增双写机制。** 产物统一归到既有的产出物机制里，**按时间保留最新**。

### 为什么不需要版本表

因为既有的 `artifact_service.py`（74 行）**已经在做这件事**：

```python
# services/artifact_service.py（既有，本次不改）
async def list_by_conversation(self, conversation_id: str) -> list[Artifact]:
    """列出对话关联的所有产出物（通过 AgentRun JOIN，按路径去重保留最新）。

    同一文件在多个 run 中被反复修改时会产生多条 Artifact（按 run 归因），
    但 File 记录只有一条（内容被覆盖）。对话级展示去重为每个路径仅保留
    最新一次写入；run_count（临时属性）标记修改过该文件的 run 数，
    供前端展示"已更新"标记。
    """
    ...
    .order_by(Artifact.created_at.asc())
    ...
    # created_at 升序遍历，后写覆盖先写 → 每个路径只剩最新一条
    latest_by_path: dict[str, Artifact] = {}
    for artifact in artifacts:
        latest_by_path[artifact.relative_path] = artifact

    latest = list(latest_by_path.values())
    for artifact in latest:
        artifact.run_count = len(run_ids_by_path[artifact.relative_path])
    return latest
```

**「按 `created_at` 升序、后写覆盖先写、每个路径只剩最新一条、`run_count` 标记改写次数」——这就是「按产物时间统一归到产物里面」。**

### 对照表

| 旧设计的版本表要提供什么 | 既有机制怎么给 |
|---|---|
| 每次生成产生一个新版本 | 每次执行产生一条新的 `harness_artifacts` 记录 |
| 当前版本指针 | 同路径 `created_at` 最新的一条 |
| 版本历史只增不删 | 历史记录本来就不删，可查 |
| 回滚到指定版本 | 直接用历史记录的 `file_id` 取回内容；或重跑该阶段 |
| 改写次数 | 既有 `run_count` |
| 内容未变不建新版本 | ⚠️ **不提供**。见下方代价 |

### 与「一次执行一条记录」的关系

`file_watcher.py` 的去重规则是 **(run_id, relative_path)**：同一次执行内同一路径只登记一条；**不同执行产生不同记录**。

```
run A 写 poc/02-业务流程/业务流程地图.yaml  →  Artifact 记录 1（created_at = t1）
run B 写 poc/02-业务流程/业务流程地图.yaml  →  Artifact 记录 2（created_at = t2）

产物列表（归并后）  该路径 1 条，取 t2 那条，run_count = 2
```

### 代价与对策

| 代价 | 对策 |
|---|---|
| ⚠️ 内容没变也会产生一条新记录 | 产生的是**记录**不是文件（File 内容被覆盖），存储开销可忽略；产物列表归并后用户只看到一条 |
| ⚠️ 不提供显式的版本号 | 需要可复现时按时间定位或重跑该阶段 |
| ⚠️ 不做「失效传播」的自动重算 | 只按时间**标记**「上游已变更」，由用户决定是否重跑 |

> **触发改回版本表的条件**：出现「需要按版本号引用产物做审计」或「需要内容哈希去重」的明确需求。当前两条都不在范围内。

## 7.3 两类容易混淆的数据

后端会存两类东西，都跟「阶段」有关，但**性质完全不同**：

|  | **产物** | **实体实例** |
|---|---|---|
| 是什么 | 六阶段**生成出来的文档** | 访谈**问到的答案** |
| 具体形态 | 业务流程 YAML、数据模型 YAML、原型 HTML | 某个付款条件的属性值 |
| 谁产生 | 模型按 `SKILL.md` 与产出规范生成 | 模型从对话内容里抽取 |
| 有版本吗 | **没有版本号**，按时间保留最新 | 随对话累积、就地更新 |
| 谁读它 | 预览区四个画布 | 本体画布 |
| 存在哪 | 工作空间文件 ＋ 产出物记录 | 工作空间文件（也是产物） |

**一句话区分**：**产物是「做出来的东西」，实体实例是「问到的内容」。**
前者按时间取最新，后者要完整度追踪（还缺哪些属性）。

> **注意**：实体实例在本设计里**也是一种产物**（写在 `poc/01-访谈/` 下的 YAML）。二者的区别是**语义**上的，不是**存储**上的——这正是「统一归到产物」的含义。

# 第八章 · 接口设计

## 8.1 新增接口

**只新增 3 个端点。**

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/poc/stages?project_id=` | 六阶段清单 ＋ 每阶段状态与产物 |
| `GET` | `/api/poc/stages/{stage_no}?project_id=` | 单阶段详情：定义、上游、产物、绑定的 `skill_id`、组装好的启动消息 |
| `POST` | `/api/poc/stages/{stage_no}/start` | 阶段启动：返回对话标识与 `skill_id` |

### `GET /api/poc/stages` 响应形状（示意）

```
{
  "stages": [
    {
      "no": 1, "key": "interview", "name": "AI 访谈",
      "skill_name": "poc-interview", "agent_code": "productDesign",
      "upstream": [], "artifact_dir": "poc/01-访谈/",
      "canvas": "ontology", "enabled": true,
      "state": "not_started",          // not_started | running | done | stale
      "skill_id": null,                 // 未装配时为 null，不是错误
      "artifacts": []
    },
    ...
  ]
}
```

**契约**：
- 未装配技能时 `skill_id` 为 `null`，**接口仍然 200**。
- 上游缺失时**不报错**，只是对应段落与产物为空。
- `state` 完全从产物推导（见 3.4），不依赖任何进度表。

### 阶段启动的语义

`POST /api/poc/stages/{no}/start` **不执行阶段**，只做三件事：

```
① 校验该阶段已装配技能（未装配 → 明确错误，提示先装配）
② 组装阶段启动消息（上游产物路径清单 ＋ 产出要求）
③ 返回 { conversation_id, skill_id, content }
```

前端拿到后，用**既有的** `/agent` 接口发出去。这样设计的好处是**阶段执行没有专用通道**——它和用户在对话里说一句话是完全同一条路径，不需要为它维护第二套生命周期。

## 8.3 流式事件

### 沿用的既有事件（**零新增**）

SDK 引擎实际发出的事件类型：

| 事件 | 含义 | 前端是否识别 |
|---|---|---|
| `run_started` | 执行开始，带 `run_id` | ❓ 未在事件分发里，但前端用它取 `run_id` |
| `thinking` | 思考过程增量 | ✅ |
| `token` | 文本增量 | ✅ |
| `subagent_token` | 子 agent 文本增量 | ❓ 未在事件分发里 |
| `tool_start` | 工具调用开始 | ✅ |
| `tool_end` | 工具调用结束 | ✅ |
| `todo_updated` | TODO 更新 | ✅ |
| `question_pending` | **待回答提问（访谈用）** | ✅ |
| `file_tree_updated` | 文件树变更 | ✅ |
| `artifact_generated` | 产物已生成 | ✅ |
| `done` | 完成 | ✅ |
| `agent_error` | 失败 | ✅ |
| `run_fatal` | 致命失败 | ❓ 未在事件分发里 |

前端 `useChatStore.js` 的事件分发认识 **10 种**：`thinking` / `token` / `tool_start` / `tool_end` / `todo_updated` / `artifact_generated` / `file_tree_updated` / `question_pending` / `done` / `agent_error`。

**结论**：阶段执行需要的事件**全部已在前端识别范围内**，不需要任何映射层。

### 与上一版设计的对比

| 上一版的内部阶段语义 | 需要映射到 | 本版 |
|---|---|---|
| 阶段开始 | `tool_start` | **不存在这个概念**——阶段就是一次 Agent 执行，模型自己决定调什么工具 |
| 阶段流式输出 | `token` | 直接用 `token` |
| 阶段结束 | `tool_end` | 不存在 |
| 抽取到实体实例 | `artifact_generated` | 写文件 → 文件监控发 `artifact_generated` |
| 产生产物快照 | `artifact_generated` | 不存在「快照」 |
| 产物文件写入 | `file_tree_updated` | 直接用 `file_tree_updated` |
| 访谈需要用户回答 | `question_pending` | 直接用 SDK 的 `question_pending` |
| 一轮全部完成 | `done` | 直接用 `done` |
| 任何失败 | `agent_error` | 直接用 `agent_error` |

**上一版「一处已知妥协」（动态步骤清单下发不出去）在本版自动消失**——因为本版不再有「后端下发的阶段清单」这回事，前端也不需要它。

## 8.4 阶段与技能的绑定契约

```
阶段定义（constants/stages.py）
    stage.key  ──▶  skill_name = "poc-" + key
                          │
                          ▼
              项目技能表 harness_myskills（按 name 查找）
                          │
                          ▼
                    skill_id（guid）
                          │
                          ▼
        POST /api/conversations/{id}/agent { content, skill_id }
                          │
                          ▼
            _resolve_system_prompt(skill_id, project_id)
                system_prompt = 平台规则 + SKILL.md
```

**四条硬约束**：

| # | 约束 | 若违反 |
|---|---|---|
| 1 | 技能**必须属于同一个项目** | `_resolve_system_prompt` 查不到会静默回退到默认提示词，阶段方法论失效 |
| 2 | 技能名必须与阶段定义一致 | 编排层找不到 `skill_id`，阶段无法启动 |
| 3 | `SKILL.md` 必须写明产物确切路径 | 进度推导失效，阶段永远显示「未开始」 |
| 4 | 技能包不得依赖外部 Python 包 | 沙箱内脚本跑不起来 |

## 9.3 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| **产物路径不稳定** | ⚠️ **高** | 一期首要验证项。`SKILL.md` ＋ 启动消息双写目标路径；失败表现为「阶段未完成」，可观测 |
